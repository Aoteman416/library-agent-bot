## 第 1 题：知识库的增量更新、版本一致性与近重复治理

**题目**：请说明 1）线上借阅规则需每月微调，若每次都全量重建 Chroma 索引会造成多长的写入阻塞？你如何设计**增量索引**（仅重算变更文档的 chunk），并解决"旧 chunk 残留 / 版本漂移"问题？给出基于版本号或时间戳的方案。 2）文档更新时，正在进行的检索可能读到"新旧混合"索引，你如何用**多版本索引（blue-green）+ 原子切换**保证一致性视图，且切换/回滚可在秒级完成？ 3）知识库出现《2024规则》与《2025规则》两份高度相似文档，会在检索时造成结果冗余甚至矛盾，你如何在入库阶段做**近重复检测（dedup）与冲突标注**？给出相似度判定与处理策略。

### 学员回答

1）全量重建索引很慢，应该改成增量。可以记录每个文档的更新时间，只把发生变化的文档重新 embedding 后写入，没变的就不动。版本用时间戳记录。
2）维护两套索引，一套旧的、一套新的，新索引建好之后把流量切过去，出问题就切回旧的。
3）用相似度判断，相似度超过 0.9 的算重复，入库时把重复文档去掉。

### 回答不足

1. **缺少层次**：全量重建的阻塞时长完全没有量化（未估算 chunk 数 × 单条 embedding 耗时），也没给"增量只重算变更 chunk"的具体删除/插入方案，只说"记录更新时间"过于表面。
2. **机制不清**：blue-green 只说"切流量"，没讲原子切换的具体实现（别名/指针切换、毫秒级回滚），也没解决"进行中检索读到新旧混合"的一致性视图问题。
3. **过于表面**：dedup 只在入库后说 sim>0.9 删掉，没说明是在**入库阶段**做；且《2024》《2025》应保留两者并标注"新版替代旧版"，而非简单删一个——冲突标注策略完全缺失。

### 最佳回答（月薪30k工程师视角）

**一、增量索引与阻塞量化**

- 全量重建成本：假设 10 万 chunk、bge-large-zh 单条 embedding ≈ 20ms（单卡），全量约 33 分钟；若锁写则期间阻塞检索写入，若在线重建则双倍内存/磁盘。生产上绝不能全量。
- 增量方案：每个 chunk 带 `(doc_id, chunk_index, content_hash, version)`。更新文档时：① 计算新 chunk 的 content_hash；② 与旧 chunk 比对，未变则跳过（省 embedding 算力）；③ 按 `doc_id` 批量 delete 该文档全部旧 chunk（彻底清掉"旧 chunk 残留"）；④ upsert 新 chunk。

```python
def incremental_index(store, doc_id, new_chunks, VERSION):
    old = store.get(where={"doc_id": doc_id})
    old_hashes = {m["chunk_index"]: m["content_hash"] for m in old["metadatas"]}
    to_upsert, to_delete = [], []
    for i, c in enumerate(new_chunks):
        h = sha256(c["text"].encode()).hexdigest()
        if old_hashes.get(i) == h:      # 未变更，跳过
            continue
        to_upsert.append((f"{doc_id}#{i}", embed(c["text"]),
                          {**c["meta"], "content_hash": h, "version": VERSION}))
        to_delete.append(f"{doc_id}#{i}")
    store.upsert(to_upsert)
    if to_delete:
        store.delete(ids=to_delete)
```

设计理由：以 `doc_id` 为删除粒度保证无残留；`content_hash` 跳过未变更 chunk 省算力；版本用**单调 version 号**（便于回滚定位），时间戳仅作"最后更新"展示。

**二、blue-green 多版本 + 原子切换**

- 用 collection 别名指向当前索引：`alias "kb_live" → collection "kb_v7"`。新版本异步写入独立 collection `kb_v8`，完成后**单次原子 rename alias → kb_v8**（毫秒级），回滚同理 rename 回 `kb_v7`。
- 进行中检索通过 alias 读 snapshot，新请求立即走新索引，避免"新旧混合"读到半更新状态。Chroma 用 `client.get_or_create_collection` + 自定义 alias 表（存 Redis）即可实现。

**三、近重复检测与冲突标注**

- 入库阶段：新 chunk 与已有 chunk 算 cosine，`sim ≥ 0.92` 判为近重复。
- 策略（不是硬删）：《2024》《2025》应 ① 保留两者；② metadata 打 `version=2025` 与 `supersede_by=<2025_doc_id>`；③ 检索时按 version 降序优先返回新版，或在 rerank 阶段给旧版降权；④ 冲突片段（如借期天数不同）单独标注"以最新版为准"，避免 LLM 把两个数字都喂进去。
- 治理：定期跑近重复扫描，把冲突对推给馆员确认，沉淀为"冲突知识清单"。

**生产经验总结**：
1. **content_hash 是关键**：没有它每次都会无脑重算全部 chunk，增量变全量。
2. **alias 切换要原子**：别用"先删后建"，会有一瞬间索引不存在导致检索 5xx。
3. **近重复别硬删**：规则更新要可回查旧版，删了出事没法对账。

## 第 2 题：混合检索的融合策略与向量索引调优

**题目**：请说明 1）你的 hybrid 检索需把向量分与关键词分拼在一起，请对比 **RRF（Reciprocal Rank Fusion）与加权求和**两种融合策略的原理差异，各自在"某一路完全失效"时鲁棒性如何，给出对比表与选型结论？ 2）Chroma 底层用 HNSW 做 ANN 检索，`ef_search` 与 `M` 是关键参数，请说明它们**分别影响召回率还是延迟**，在 100 万条规模下如何调参，并解释为何"召回率随 ef_search 增大而饱和"？ 3）相似度度量用 cosine 还是内积（IP）？当 Embedding 未归一化时二者结果一致吗？选错度量会怎样让"最相似"排序崩塌，请给出归一化校验代码。

### 学员回答

1）RRF 比加权求和好，因为它不依赖分数。某一路失效时 RRF 不受影响。
2）`ef_search` 影响召回率，`M` 影响延迟。100 万条时把这两个调大一点。
3）用 cosine。未归一化时二者差不多。本项目用 bge 直接算就行了。

### 回答不足

1. **机制不清**：RRF 与加权求和的原理差异没有公式级说明，缺对比表与明确选型结论；"某路失效"时加权求和到底怎样被污染没讲。
2. **事实错误**：`M` 影响的是**建图阶段**（召回上限/内存），不是"延迟"；认为"调大一点"会同时改善召回和延迟是错的——`ef_search` 增大召回升但延迟也升。
3. **场景缺失**：归一化校验代码完全缺失；"未归一化时二者差不多"是**错误**的——IP 在未归一化时会被向量范数（长度）_bias，排序会崩；且 bge 系列必须 L2 归一化否则掉点明显。

### 最佳回答（月薪30k工程师视角）

**一、RRF vs 加权求和**

- RRF：`score(d) = Σ 1/(k + rank_i(d))`，`k=60`，**只看排名不看分数**。
- 加权求和：`score = Σ w_i · norm(score_i)`，依赖分数尺度，需各自归一化。

| 维度 | RRF | 加权求和 |
|------|-----|---------|
| 分数尺度依赖 | 无（仅 rank） | 强（必须 min-max/softmax） |
| 某一路完全失效 | 该路 rank 靠后贡献≈0，不影响 | 若该路返回异常值/未归一化会污染总分 |
| 实现复杂度 | 低 | 中（需归一化管道） |
| 调参 | 仅 k | 多组 w |

选型：**生产默认 RRF**（对某路失效鲁棒）；需要"向量命中必须加权"时再用 RRF + 业务加权混合。

**二、HNSW 调参（100 万条）**

- `M`：**建图阶段**每个节点最大连接数。M 大→召回上限高、内存大、构建慢。100 万条 `M=16~32`。
- `ef_search`：**查询阶段**动态候选集大小。大→召回高、延迟高。100 万条 `ef_search=128~256`。
- 为何饱和：超过真实近邻聚集半径后，继续扩候选集只是纳入更远节点，命中率不再升而延迟线性增长。生产按"召回达标的最小 ef_search"设（如 90% 召回对应 128）。
- Chroma 通过 collection metadata `hnsw:M` / `hnsw:ef_search` / `hnsw:space` 配置。

**三、cosine vs IP 与归一化校验**

- cosine = 归一化后的 IP。未归一化时 `IP = |a||b|cosθ`，**长文本向量（范数大）会被 IP 偏向**，排序崩塌。
- bge 训练用 cosine，**推理端必须 L2 归一化**，否则效果掉一档。

```python
import numpy as np
def check_normalized(embs: np.ndarray, tol: float = 1e-3) -> bool:
    norms = np.linalg.norm(embs, axis=1)
    bad = np.where(np.abs(norms - 1.0) > tol)[0]
    assert len(bad) == 0, f"{len(bad)} 条未归一化, 示例norm={norms[bad[:3]]}"
    return True
# 入库前与查询前都校验，从源头杜绝尺度污染
assert check_normalized(query_emb) and check_normalized(doc_embs)
```

**生产经验总结**：
1. **RRF 是默认安全牌**：别一上来就加权，加权求和的归一化坑最多。
2. **ef_search 按召回曲线定**：拍脑袋 512 既慢又无收益。
3. **bge 必须归一化**：这是血泪坑，不归一化效果直接掉一档。

## 第 3 题：多轮对话的摘要压缩、流式落库时序与记忆分层

**题目**：请说明 1）当对话超过 `MAX_HISTORY_TOKENS` 时模板用硬截断丢弃早期内容，但早期可能含关键约束（如"我只问社科类图书"）。你如何用**对话摘要压缩（summary）替代硬截断**，并说明摘要本身引入的"信息损失/幻觉"风险与校验手段？ 2）流式输出下 assistant 回复逐 token 生成，你**何时把这条消息落库**——生成前、流式中、还是 done 之后？不同选择在"用户断线/服务崩溃"时分别导致什么数据问题（丢消息/重复消息）？ 3）同一用户同时开 Web 与小程序两个终端，两个 session 历史会互相干扰吗？你如何设计**用户级长期记忆与会话级短期记忆的分层**，避免跨会话上下文污染？

### 学员回答

1）用摘要代替截断，把前面的对话总结一下再放进去。
2）在流式中把每个 token 存到数据库。
3）两个 session 因为是不同 session_id，所以互不干扰。

### 回答不足

1. **缺少层次**：摘要的"信息损失/幻觉"风险只字未提，更没有校验手段（如只压缩不允许推断、原始消息归档、关键约束结构化抽取）。
2. **过于表面**：落库时机只说"流式中逐 token 写"，既没分析三种时机的断线/崩溃后果，也没考虑逐 token 写 DB 的吞吐灾难。
3. **机制不清**：第 3 问仅说"session_id 不同不干扰"，但没区分**用户级长期记忆（偏好"只问社科类"）与会话级短期记忆**，跨终端真正的风险在长期记忆如何合并而非会话级。

### 最佳回答（月薪30k工程师视角）

**一、摘要压缩替代硬截断**

- 累计 token > `MAX_HISTORY_TOKENS` 时，把最早 N 轮交 LLM 生成 `summary`（含关键约束"用户仅关注社科类"），保留最近 K 轮原文。
- 风险：摘要可能丢细节或幻觉（编造约束）。校验：① prompt 限定"仅复述已出现事实，不允许推断"；② **原始消息归档到 MySQL `messages` 表**，summary 仅作压缩视图，可审计回溯；③ 关键约束用结构化 slot（`constraint` 字段）单独抽取存储，不依赖自由文本摘要。

**二、流式落库时序**

| 时机 | 断线/崩溃后果 | 结论 |
|------|--------------|------|
| 生成前建空记录(status=generating) | 留未完成记录，需定时清理孤儿 | **推荐** |
| 流式中逐 token 追加 | 吞吐灾难、易重复写 | 不推荐 |
| done 后整条写 | 崩溃则整条丢失，用户看到答案却无记录 | 可接受但丢日志 |

- 推荐：生成前 `INSERT` assistant 消息(status=generating, content="")；流式过程只在内存/Redis 累积；`done` 时 `UPDATE content+status=done+usage`。断线靠 `event_id` 重连拉已落库内容避免重复。崩溃由定时任务清理 `status=generating` 超 5min 孤儿记录。
- 去重：用 `(session_id, turn_id, event_id)` 幂等，重试不重复插入。

**三、用户级 vs 会话级记忆分层**

- 会话级（短期）：`session_id` 隔离，Web/小程序不同 session **天然不互相污染**——这点正确，但要明确"会话级不会跨终端污染"。
- 用户级（长期）：跨 session 的用户画像/偏好（"只问社科类""常用 3 楼"）存 `user_profile` 表，该用户所有 session 加载时合并。
- 防污染：长期记忆是"只读上下文注入"，不反向写入会话原文；用户在任一端改偏好全端生效；冲突时长期记忆优先级低于当前会话的显式最新指令。

**生产经验总结**：
1. **原始消息必须落库归档**：summary 只是压缩视图，不能替代原始记录，否则无法审计回溯。
2. **生成前建记录 + done 更新** 是数据安全与性能的平衡点。
3. **长期记忆别反向污染会话**：只读注入，避免一个终端的试探性提问污染另一终端。

## 第 4 题：多 LLM Provider 故障转移、SSE 断线恢复与流式结构化

**题目**：请说明 1）单个 LLM Provider 有 quota/region 故障风险，你如何设计**多 Provider 故障转移链（primary→fallback→fallback）**，切换时"已发出的一半答案"如何处理（续写 vs 重启 vs 报错），且 system prompt + 已检索 context 如何无缝传递？ 2）SSE 是单向长连接，前端网络抖动会断，你如何设计**断线恢复与去重**——重连后如何续传剩余 token 而非从头，且避免答案重复拼接？给出基于 event_id / offset 的方案。 3）你要求 LLM 返回**结构化 JSON（含 sources 字段）**供前端渲染卡片，但 JSON 与逐 token 流式天然冲突（未闭合无法解析），你如何兼顾"流式体验"与"结构化输出"，并防止前端渲染半截 JSON 崩溃？

### 学员回答

1）配置多个 provider 按顺序试，第一个挂了用第二个。
2）SSE 断线前端自动重连就行。
3）让 LLM 直接输出 JSON，前端解析渲染卡片。

### 回答不足

1. **部分遗漏**：第 1 问"已发出一半答案怎么办"完全没答（续写/重启/报错三选一及其代价）；system prompt + context 如何"无缝传递"也没给具体解耦方案。
2. **机制不清**：SSE 恢复只说"重连"，没给续传 offset / 去重机制，重连后必从头重发导致答案重复拼接。
3. **场景缺失**：第 3 问只说"让 LLM 输出 JSON"，但没解决未闭合 JSON 无法 `json.loads`、前端渲染半截崩溃的问题，缺两段式/NDJSON/流式解析器等解法。

### 最佳回答（月薪30k工程师视角）

**一、多 Provider 故障转移**

- 链：`primary(deepseek) → fallback(qwen) → fallback(gpt)`，用 circuit breaker 记录各 provider 错误率/延迟做 failfast。
- "已发出一半答案"怎么办：流式中途切 provider **几乎不可能续写**（不同模型上下文态不同）。决策：① 若 < 首句（尚无实质内容）→ 透明重启（前端收 `error:provider_switch` 重发）；② 若已出大半 → 终止当前流，返回"服务波动，已重新生成"并重发整条；③ **system prompt + 检索 context 作为独立 payload，切换时完整重传**，不依赖上一家模型的隐状态。
- 实操：`LLMClient` 层 `for p in chain: try: stream=p.generate(prompt, context); break`，prompt/context 与 provider 解耦。

**二、SSE 断线恢复与去重**

- 每个回答分配 `event_id`（=turn_id），token 带 offset：`data:{"event_id":"t123","offset":5,"content":"好"}`。
- 前端断线重连带 `Last-Event-ID: t123:5`，服务端从该 offset 后续传（已生成完则重放 Redis 缓存的剩余 token；仍生成中则继续推）。
- 去重：前端按 `(event_id, offset)` 幂等，重复到达忽略；服务端对已完成 turn 的 token 用 Redis 缓存整段，重连时快进。
- 注意：SSE 默认无重发保证，靠 **offset + 缓存** 实现"至少一次 + 去重"。

**三、流式体验 + 结构化 JSON**

冲突本质：JSON 未闭合无法 `json.loads`。三种解法：

| 方案 | 做法 | 评价 |
|------|------|------|
| 两段式 | 先流 `event:token` 文字，done 前发 `event:structured` 带完整 JSON 卡片 | **最稳，推荐** |
| NDJSON | 每行一条 `{"type":...}`，逐行解析，半截行丢弃重连补齐 | 简单通用 |
| 流式 JSON 解析 | ijson 边收边解析已闭合字段 | 体验最好但复杂 |

- 防前端崩溃：永远 `try/catch` 包裹 `JSON.parse`，渲染前用 pydantic 校验 `sources` 字段 schema。
- 本项目直接用**方案 1**（契合现有 SSE `token/source/done` 事件设计）。

**生产经验总结**：
1. **流式中途切模型 = 重发**：别幻想续写，不同模型续不上。
2. **offset 是 SSE 去重基石**：没有它重连必重复拼接。
3. **结构化用两段式最省心**：先文字后 JSON 卡片，前端零崩溃风险。

## 第 5 题：意图识别的置信度校准、混合意图编排与在线新意图发现

**题目**：请说明 1）意图识别模型输出的"置信度"往往**校准不良**（0.7 其实不可信），你如何做**置信度校准（Platt scaling / 温度扰动投票）**，并据此动态决定"直接路由 / 反问 / 走兜底"，而非拍脑袋设 0.5 阈值？ 2）真实请求常是混合意图（如"查《三体》在架吗，顺便说下寒暑假规则"），你如何做**意图拆分与编排（先 RAG 检书目 + 再 RAG 答规则 + 合并）**而非二选一？给出编排状态机或 DAG 设计。 3）上线后出现训练时未见过的**新意图**（如突然大量"预约研讨间"），你如何做**在线新意图发现与冷启动**（聚类未命中样本 + 人工打标回流），避免新需求被永久误判为"知识问答"？

### 学员回答

1）设个阈值 0.5，高于就路由，低于就转人工。
2）多个意图都处理一下就行。
3）用聚类发现新意图，聚出来新类就加上。

### 回答不足

1. **事实错误/过于表面**：直接拍 0.5 阈值，完全没做校准（Platt / 温度扰动投票），未指出 softmax 概率未校准的问题。
2. **机制不清**：混合意图只说"都处理"，没给编排 DAG/状态机，也没说并发执行与合并策略。
3. **场景缺失**：新意图只说"聚类加类"，没给**冷启动回流**与"避免被永久误判为知识问答"的保守处理机制（先 pending 后固化）。

### 最佳回答（月薪30k工程师视角）

**一、置信度校准**

- 问题：分类头 softmax 概率未校准（0.7 实际准确率可能仅 0.55）。
- Platt scaling：用验证集训练逻辑回归把 raw logit 映射到校准概率 `p = 1/(1+exp(A·s+B))`。
- 温度扰动投票：同一 query 用 `T∈{0.8,1.0,1.2}` 多次采样，取多数 + 一致性作为置信；一致性低 → 降置信。
- 动态路由（拒绝固定 0.5）：`calibrated_p≥0.9` → 直接路由；`0.6~0.9` → 路由但附"可能不准确"；`0.4~0.6` → 反问澄清；`<0.4` → 兜底/转人工。

**二、混合意图编排（DAG）**

"查《三体》在架吗，顺便说下寒暑假规则" = `[馆藏检索]` + `[政策FAQ]`。

```
意图A(馆藏:三体在架) ─┐
                        ├─→ merge_node ─→ 统一回复
意图B(规则:寒暑假)  ─┘
```

- 实现：LLM/拆词识别多意图 → 生成 task list → `asyncio.gather` **并发**跑两个 RAG 分支（各自检索+生成片段），`merge_node` 用 LLM 按"先答在架状态，再答规则"顺序合成，避免二选一丢信息。
- 状态机：`INIT→PARSE→[DISPATCH 并行]→MERGE→RESPOND`，任一分支失败降级为"部分回答 + 提示"。

**三、在线新意图发现与冷启动**

- 未命中（所有意图 `calibrated_p < 0.4`）的样本进 `unresolved_questions` 表（项目已有）。
- 离线聚类：每日对 unresolved 做 embedding + HDBSCAN，簇规模超阈值（如 >50/天）且人工标注为新意图（"预约研讨间"）→ 加入意图标签，回流训练/提示词。
- 防永久误判：对新簇先**保守处理**（标 `pending_intent`，走 FAQ+RAG 兜底但不强行归类为已知意图），确认后再固化；监控"新意图占比"超基线告警。

**生产经验总结**：
1. **别信 raw softmax 概率**：校准后路由质量肉眼可见提升。
2. **混合意图用 DAG 并发**：串行拼会慢且丢上下文。
3. **新意图先保守后固化**：宁可先当未知，也别强行塞进错误意图。

## 第 6 题：多租户知识隔离、向量反推隐私与审计防篡改

**题目**：请说明 1）系统未来服务**多个分馆（多租户）**共用一个 Chroma 实例，如何防止租户 A 的检索命中租户 B 的私有知识（如内部采购价）？请对比 metadata 隔离、collection 隔离、查询时强制 tenant_id 过滤三者的权衡与实现。 2）向量本身可能被**反推出原文片段（embedding inversion）**，当知识库含敏感内容时，你如何在"可用检索"与"防向量泄漏"间取舍？是否考虑加密 embedding 或查询时脱敏？ 3）操作审计要求**日志不可篡改可追溯**，攻击者在拿到数据库写权限时可静默改写 `operation_logs`。你如何用 **WORM 存储 / 哈希链 / 独立审计通道**保证审计完整性，且不影响写入性能？

### 学员回答

1）在查询时加上 tenant_id 过滤条件就行。
2）向量可能被反推出来，所以要注意。
3）给日志加个 hash 防止被改。

### 回答不足

1. **过于表面**：只说"加 tenant_id 过滤"，没对比三种隔离方案（metadata / collection / 查询时强制）的权衡，也没讲如何实现双保险。
2. **缺少层次**：向量反推隐私只说"要注意"，没给任何取舍方案（脱敏入库 / 加密 embedding / 差分隐私），敏感字段到底进不进向量库没结论。
3. **机制不清**：审计只说"加 hash"，但单 hash 可被攻击者改了 log 再重算 hash 绕过——缺 WORM / 哈希链 / 独立通道，且没考虑性能。

### 最佳回答（月薪30k工程师视角）

**一、多租户隔离三方案对比**

| 方案 | 隔离强度 | 成本 | 适用 |
|------|---------|------|------|
| metadata `tenant_id` | 弱（靠查询正确，漏写 where 就串） | 低，单 collection | MVP |
| collection 隔离 | 强（物理分离） | 高（N 个 collection） | 强合规场景 |
| 查询时强制 `tenant_id` | 中（中间件注入兜底） | 低 | 推荐生产 |

- 推荐：**collection 按租户建**（强隔离）+ 查询中间件强制注入 `tenant_id` 双保险。Chroma 用 `client.get_collection(f"kb_{tenant_id}")`，retriever 层用 `Depends` 注入 tenant，杜绝漏过滤。

**二、向量反推隐私**

- embedding inversion 可近似还原原文片段（尤其高维短文本）。
- 取舍：① **查询时脱敏**——入库前敏感字段（采购价）单独存关系库，向量库只存脱敏文本，检索命中后按权限 join 明文；② 加密 embedding（SE）成本高、召回降，一般不做；③ 差分隐私加噪——牺牲部分召回换隐私，适合强合规。
- 本项目：内部采购价等敏感字段**不进向量库**，只在 metadata 留 category，明文走 MySQL 按需授权读取。

**三、审计防篡改（WORM / 哈希链 / 独立通道）**

- 单 hash 不够：攻击者改 log 再重算 hash 即可绕过。
- **哈希链**：每条 log 存 `prev_hash + 本记录 hash`，形成链，改任一条后续 hash 全断裂可检测。
- **WORM**：写一次读多次存储（对象存储合规模式/区块链），禁止 delete/update。
- **独立审计通道**：log 除写主库外，异步推一份到独立 sink（Kafka→独立审计库），主库被攻破也改不了副本。
- 性能：哈希链主库写时同步算（开销可忽略）；WORM/独立通道异步，不阻塞主写。

**生产经验总结**：
1. **tenant_id 必须中间件强制注入**：靠人写 where 必串库。
2. **敏感字段别进向量库**：向量最易被反推，明文走关系库授权读。
3. **哈希链 + 独立通道**才是真防篡改，单 hash 是自欺。

## 第 7 题：版本化回归评测、LLM-as-Judge 偏差缓解与离线/线上鸿沟

**题目**：请说明 1）你优化 Prompt 修好一类 bad case，却可能**把已答对的题答错（回归）**，你如何维护一份**版本化回归测试集（regression gold set）**，在每次 prompt/检索改动时自动跑回归，并给出"不允许分数低于基线"的卡口（gate）设计？ 2）用 LLM-as-Judge 打分时，裁判模型存在**位置偏差（偏好首答案）、自我偏好、冗长偏好**，你如何设计 judge pipeline 缓解（交换顺序、双盲、rubric 锚定）？ 3）离线指标（召回率 90%）很好但线上**自助解决率仅 60%**，离线评测与线上体验的鸿沟从哪来？你如何建立**线上 A/B 与离线指标的映射**，并用"用户追问/转人工"等线上信号反推离线评测集的盲区？

### 学员回答

1）每次改 prompt 都跑一遍测试集看效果。
2）judge 用 LLM 打分，多打几次取平均。
3）离线高线上低是因为线上用户不一样。

### 回答不足

1. **机制不清**：回归测试集 + gate 没给具体实现，"不允许分数低于基线"的卡口（CI 阻塞）完全没提，只说"跑一遍看效果"无法防回归。
2. **过于表面**：Judge 只说"多打几次取平均"，没针对位置/自我/冗长三种偏差给缓解手段（交换顺序/双盲/rubric 锚定）。
3. **缺少层次**：离线线上鸿沟分析太浅（只说"用户不一样"），没给 A/B 映射机制，也没说如何用线上"追问/转人工"信号反推评测集盲区。

### 最佳回答（月薪30k工程师视角）

**一、版本化回归测试集 + gate**

- 维护 `regression_gold_set`（jsonl：`query / expected_answer / 关键约束 / 禁止项`）。每次改 prompt/检索，CI 自动跑全量回归，指标：答案准确率、幻觉率、引用准确率。
- gate 设计：基线如 `acc≥0.92`，新版本低于基线 → CI 失败阻塞合并（"不允许分数低于基线"）。

```python
def test_regression_not_below_baseline():
    results = run_suite("regression_gold_set")
    assert results["accuracy"] >= BASELINE_ACC, f"回归跌破基线 {results['accuracy']}"
    assert results["hallucination"] <= MAX_HALLU
```

**二、LLM-as-Judge 偏差缓解**

| 偏差 | 缓解 |
|------|------|
| 位置偏差 | 交换 A/B 顺序各评一次，取平均 |
| 自我偏好 | judge 用与生成**不同**的模型 |
| 冗长偏好 | rubric 锚定"简洁正确 > 啰嗦"，按点打分 |

- pipeline：**双盲**（隐藏哪份是实验组）→ 交换顺序两次评分 → 用 rubric（"是否基于检索内容/有无幻觉/引用是否正确"）逐维打分 → 取均值并记录方差。

**三、离线 ↔ 线上鸿沟与映射**

- 鸿沟来源：离线用"理想 query + 标准答案"，线上是真实噪声 query、多轮、用户耐心；离线召回 90% 但自助解决率 60% → 差在"答非所问/格式差/用户没看懂"。
- 映射：线上埋点"是否追问/转人工/点踩"作为真实标签；把高追问率问题回捞做离线 case 分析，补全 gold set 盲区（口语化问法、多轮指代）。
- A/B：新版本同时跑离线回归 + 小流量线上（5% 自助解决率 vs 基线），离线过了但线上掉 → 不发布。

**生产经验总结**：
1. **gate 必须卡死基线**：否则"修一类坏一类"悄悄进生产。
2. **Judge 要交换顺序 + 双盲**：否则位置/自我偏好污染结论。
3. **线上信号是离线集的氧气**：不回流真实 query，评测集永远脱离战场。
