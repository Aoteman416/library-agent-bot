## 第 1 题：故障排查实战——从告警现象反推根因

**题目**：请说明 1）线上现象：某天上午 10 点，系统 **P99 延迟从 800ms 涨到 12s**，但 QPS、错误率、CPU、内存**一切正常**，LLM Provider 侧也返回正常。请给出你的**排查决策树**（前 5 步你会看什么），列出最可能的 3 个根因及各自的验证方法？ 2）运营投诉"客服最近总答非所问"，但**所有技术指标（召回率、幻觉率、QPS、延迟）在监控上都正常**。你会怀疑什么？请设计一套**能暴露这类"静默降质"的可观测性**。 3）知识库昨晚新增 200 篇文档，今天"开放时间"类问题开始答错。请设计一条**能定位到"是哪篇文档/哪个 chunk 污染了检索"的排查链路**，说明你的 trace 需要记录哪些字段。

### 学员回答

**1）P99 从 800ms 涨到 12s 的排查**

前 5 步我会这样看：
1. 先看监控大盘，确认是不是告警误报，看 P99 是持续性还是尖刺。
2. 看外部依赖：LLM Provider、向量库、MySQL、Redis 的监控，看谁慢了。
3. 看应用日志：有没有 ERROR、慢查询、超时日志。
4. 看最近变更：代码发布、配置变更、知识库更新，10 点这个时间点可能是定时任务或运营操作。
5. 看限流和队列：是不是限流把请求排队了。

最可能的 3 个根因：
- 根因一：LLM 调用超时。验证：看 LLM 相关日志耗时，或直接 curl 一下 LLM 接口看延迟。
- 根因二：向量检索变慢，知识库变大导致检索时间变长。验证：单独压测检索接口看耗时。
- 根因三：数据库连接池打满。验证：看连接池活跃连接数。

**2）静默降质**

技术指标正常但用户投诉答非所问，我怀疑是知识库内容本身有问题（过期、错误文档），或者用户实际问的问题跟我们评测集里的不一样、评测集覆盖不到。

可观测性设计：加用户点踩反馈统计，按天看趋势；另外每天人工抽检一部分对话来打分。

**3）知识库污染排查**

- 先看昨晚新增的 200 篇文档，人工检查有没有跟"开放时间"冲突的。
- 用"开放时间"相关问题去检索，看 top 结果是不是新文档。
- 确认是新文档导致的，就先下线这批文档，重新建索引。

trace 需要记录：query、检索到的 doc_id、score、最终答案。

### 回答不足

1. **缺少层次**：第 1 问的"前 5 步"是通用排查清单（看监控/看日志/看变更），任何人都背得出来，完全没有利用题干给出的**最强约束**——QPS、错误率、CPU、内存全部正常。由 Little's law（并发 = 吞吐 × 延迟），吞吐不变而延迟暴涨意味着"在途请求数"暴涨；CPU 不变意味着它们**不是在算，是在等**。所以第一假设应该是"排队"，而不是"某个组件慢"。你直接跳去猜 LLM 慢、检索慢，而这两者几乎必然伴随 CPU 或上游指标变化，与题干矛盾。
2. **事实错误**："LLM Provider 侧返回正常 = LLM 没问题"是错的。Provider 控制台只能证明它自己没报错，证明不了你到它之间的连接池、DNS、TLS、排队与重试放大是正常的。该看的是**我方视角**的 connect 时间、TTFB、总耗时、重试次数。
3. **过于表面**：第 2 问只给了"点踩统计 + 人工抽检"两条，而人工抽检是抽样审计（发现周期以天计、覆盖率低），不是可观测性。题目要求的是**无标注的线上代理指标**（忠实度/依据率、拒答率、重复提问率、检索分数分布漂移）+ **分层 golden set 回归** + **影子回放**，你一条都没给。
4. **部分遗漏**：第 3 问的 trace 字段只列了 query/doc_id/score/answer，缺了定位污染最关键的四个：`kb_version`/`index_version`（把问题关联到"昨晚那次入库"）、`chunk_id`（doc 级定位不到具体是哪一段被切断）、`used_in_prompt`（检索到了但没进 prompt 的 chunk 不是凶手）、`ingested_at`（时间切片过滤）。
5. **机制不清**：定位污染靠"人工检查 200 篇文档"——200 篇能人看，2 万篇呢？缺可规模化的手段：**消融实验**（把可疑文档从索引摘掉重跑同一批问题，看指标是否恢复）。相关性不等于因果，只有消融给出的是因果证据。
6. **场景缺失**：完全没提本项目真实的两个坑——`rag_service._template_answer`（离线模板）会原样拼接 chunk，污染 chunk 会被 100% 复述；以及 `SemanticCache` 缓存了被污染的答案后，**即使修好知识库，命中缓存的用户还在继续拿错答案**。

### 最佳回答（月薪30k工程师视角）

**一、P99 劣化的决策树与三大根因**

先做推理：QPS 不变、CPU 不变、内存不变、错误率不变，**只有 P99 涨了 15 倍**。这说明请求不是在"算"，是在"等"。这个判断能直接砍掉一半排查路径。

| 步骤 | 看什么 | 能排除/锁定什么 |
|---|---|---|
| 1 | 分位数下钻：P50/P90/P99 拆开，再按实例、路由、意图、用户群拆 | P50 不动只有 P99 动 → 长尾/排队；只有个别实例慢 → 单实例状态（GC、热 key、本地缓存未预热） |
| 2 | **饱和度与等待指标**（不是使用率）：线程池/连接池 in-use 与 wait_time、httpx 连接上限、事件循环 lag、GC 停顿 | CPU 正常但 `pool.wait_time` 的 P99 与延迟同形状 → 确认排队，并定位到具体池 |
| 3 | 变更关联：近 24h 的代码/配置/**知识库**/模型变更；用 trace 对比变更前后各 span 的耗时 delta | 有变更 → 直接看变更内容；无变更 → 转查容量与数据增长 |
| 4 | 抓一条慢 trace 做自顶向下分解，重点算 **gap = 墙钟 − Σ(span self time)** | gap 大 → 排队/事件循环阻塞；gap 小且某 span 独占 → 该组件慢 |
| 5 | 我方视角的外部依赖：connect 时间、TTFB、总耗时、重试次数、响应 token 数、是否被流式缓冲 | 区分"上游慢"与"我方到上游的链路慢/请求被放大" |

三个最可能的根因：

| 根因 | 为什么符合"一切正常" | 验证方法 |
|---|---|---|
| **① 连接池/线程池耗尽（排队）** | 请求在队列里等着，不占 CPU、不报错、QPS 还能维持，只拖长尾部——四个异常指标一个都不碰 | 打点 `pool.wait_time`/`in_use`；压测爬坡看延迟是否"阶跃"；`py-spy dump` 看线程卡在 `acquire`；把池调大一倍看 P99 是否应声回落 |
| **② 同步 CPU 密集代码阻塞事件循环** | 单核打满在 4 核机器上是 25%，"CPU 正常"；但事件循环被卡住，全体请求等一轮 | 监控 event loop lag（50ms 采样打点）；`py-spy top` 看是否卡在 embedding；挪到 `run_in_threadpool` 后对比 P99 |
| **③ LLM 的我方侧长尾** | Provider 只看自己的成功率与延迟；生成 token 数突增、SSE 被网关缓冲、超时重试放大，它全看不见 | 记录 `completion_tokens` 与首包时间；统计 retry 次数与"请求放大比"；对比流式 vs 非流式 P99；看 token 分布是否出现长尾 |

> 本项目 `app/core/llm_client.py` 的真实隐患：`LLMClient` 用**默认** `httpx.AsyncClient`（`max_connections=100`），而 `LLM_TIMEOUT=30s`——12s 的 P99 恰好落在"连接池被 30s 超时请求占满"这个剧本里，这是最该先验的一条。

**二、静默降质的可观测性**

根因判断：技术指标健康说明**系统按设计工作了**，答非所问说明**设计或数据本身有问题**。APM 测的是"请求有没有被正确处理"，测不到"答案对不对"。四层设计：

1. **无标注线上代理指标**（每天全量算）：
   - 忠实度/依据率：把答案拆成断言，用小 NLI 模型判每条断言能否在**进 prompt 的 chunk** 里找到支撑，取最小值。
   - 拒答率/兜底率：`mode=template` 与"抱歉我没找到"的占比。
   - 重复提问率：同一用户 60s 内换说法再问相似问题。
   - 检索分数分布漂移：看 P10/P50 与整体分布的 PSI/KL，不看均值。
2. **分层 golden set 回归**：头部（Top 20 意图 × 30 条）+ 长尾 200 条 + 历史 badcase 50 条，每次**代码发布或知识库更新**都触发。judge 必须先与人工标注对齐（一致率/κ > 0.8）才准用。
3. **影子回放**：把线上真实 query 回放到新版本离线打分对比，不影响用户。
4. **人工锚点**：每天随机抽 50 条由馆员打标，用于校准"代理指标是否失真"。

告警原则：**分位数 + 环比 + 分层**，不告警均值；每条告警必须配 runbook。

**三、污染 chunk 的溯源链路**

trace 必埋字段（缺一个就定位不了）：

```python
{
  "trace_id": "...", "turn_id": "...",
  "query": "图书馆几点开门", "intent": "opening_hours",
  "kb_version": "2026-09-05",            # 关联"昨晚那次入库"
  "index_version": "idx-2026-09-06-013",
  "embedding_model": "bge-large-zh-v1.5",
  "chunks": [
    {"doc_id": "kb/open_hours.md", "chunk_id": "kb/open_hours.md#c3",
     "version": "v7", "ingested_at": "2026-09-05T22:11:03+08:00",
     "rank": 1, "cosine": 0.81, "rerank_score": 0.93, "used_in_prompt": True},
  ],
  "answer": "...", "sources": [...], "user_feedback": None,
}
```

五步定位（从相关到因果）：

1. **复现收敛**：用出错的"开放时间"问题批量跑检索，dump `used_in_prompt=True` 的 chunk。
2. **时间切片**：按 `ingested_at >= 昨晚` 过滤，看坏样本命中的 chunk 是否全来自新文档。
3. **按 doc 聚合**：统计每个 `doc_id` 在坏样本中的出现频次 → Top-N 嫌疑文档；再看 `chunk_id` 定位到具体段落（八成是被切断的表格，或 FAQ 里残留的旧时间表）。
4. **消融验证（决定性）**：建一个排除这些 doc 的影子索引重跑 → 指标恢复 = 因果成立；不恢复 = 另有真凶（可能是 prompt 或 `SemanticCache`）。
5. **修复与防复发**：打 `deprecated` / 加生效时间；**同步清语义缓存**；badcase 固化进 golden set；入库流水线加冲突检测。

**生产经验总结**：
1. **CPU 正常而 P99 暴涨，先怀疑"等"而不是"算"**——排队、池、锁、事件循环阻塞，占我见过的同类故障八成。
2. **"上游正常"要永远换成"我方视角的上游"**——Provider 看不到你的连接池、DNS、TLS 和重试放大。
3. **质量监控必须"无标注代理指标 + 人工锚点"双轨**，只有前者会被自信的胡说骗过，只有后者发现太晚。
4. **污染定位的关键词是消融不是相关性**——能摘掉再跑一遍，才叫证据。

## 第 2 题：成本治理——LLM/RAG 的 Token 经济学

**题目**：请说明 1）请对系统做**单次对话的成本建模**：列出全部成本构成（Embedding、向量检索、prompt token、completion token、重排、存储与运维），给出量级估算公式，并指出**哪个环节是成本大头**、为什么？ 2）给出 3 个降本手段并对比收益与副作用：**语义缓存（semantic cache）**、**模型分级路由（简单问题走小模型）**、**prompt/上下文压缩**。请给出对比表与你的组合策略。 3）业务方要求"**成本降 50% 但答案质量下降不超过 3%**"，你如何**量化验证**这个目标？若压测后发现降本导致**长尾问题**质量掉了 15%（头部问题只掉 1%），你如何决策并向业务方沟通？

### 学员回答

**1）单次对话成本建模**

成本构成：Embedding（文档和 query 转向量）、向量检索、prompt token、completion token、重排、存储与运维。

公式：单次成本 = embedding 成本 + 检索成本 + prompt token × 单价 + completion token × 单价 + 存储运维摊销。

大头应该是 **completion token**，因为输出 token 单价比输入贵好几倍。

**2）三种降本手段**

| 手段 | 收益 | 副作用 |
|---|---|---|
| 语义缓存 | 命中后不用调 LLM，省 token 也降延迟 | 相似问题可能误命中 |
| 模型分级路由 | 简单问题走便宜的小模型 | 小模型能力弱，可能答错 |
| prompt 压缩 | 减少输入 token | 压缩可能丢信息 |

组合策略：三个都上，先做语义缓存（最省），再做分级路由，最后做压缩。

**3）量化验证与决策**

验证：准备一个评测集跑一遍算准确率，对比降本前后分数，看下降是否在 3% 以内；成本看每千次对话花多少钱。
若长尾掉 15%、头部掉 1%：整体平均可能只掉 3% 左右，但我不接受，因为长尾答错对体验伤害很大。我会跟业务方说明，建议只降 30%，或者长尾继续用原来的大模型。

### 回答不足

1. **事实错误**："大头是 completion token"在本项目是错的。输出单价确实贵 4 倍，但**输出量远小于输入量**：`TOP_K=10` × chunk 200 字 ≈ 3000 token 上下文 + system + 多轮 history，输入轻松 2k-4k token，输出通常只有 200-400 token。**输入（prompt）才是大头**——这正是 TOP_K 从 3 调到 10 会让成本翻倍的原因。结论必须算出来，不能靠"输出更贵"的直觉。
2. **缺少层次**：公式只写到"各项 × 单价"，没有展开到**可优化的变量**：`N_context = TOP_K_used × L_chunk`、`N_history = turns × avg_len`。不展开到变量级就不知道该砍哪一段。另外完全漏了**自托管算力成本**——重排（cross-encoder）要对每个候选做一次前向，10 个候选 = 10 次推理，它不吃 token 但吃 CPU，是本地部署下的隐形大头。
3. **过于表面**：三种手段的副作用各写了一句正确的废话，既没量化，也没给**缓解副作用的工程手段**（语义缓存怎么防误命中？分级路由怎么防误判？）。只列缺点不给解法等于没答。
4. **概念精度不足**：组合策略"三个都上"是错的优先级。正确顺序是**先无损、后有损**：动态 TOP_K/历史滑窗（≈零损失）→ 语义缓存（收益大但有静默降质风险）→ 分级路由（带兜底）→ 有损压缩（最后且必须 A/B）。你把风险最高的手段排在了免费手段前面。
5. **部分遗漏**：验证方法只说"跑评测集看准确率"，缺四件事：① judge 是否已与人工校准（老问题复发）；② 分层出分而非只看总分；③ **统计显著性**——3% 的差异在小样本上完全是噪声，必须给 bootstrap 置信区间；④ 成本侧要用真实 trace 的 token 分布核算。
6. **场景缺失**：没提"长尾崩了"该怎么**分层止损**（不是全局回滚，而是按难度路由：长尾/低置信强制走原链路），也没提给业务方的沟通应该是**成本-质量 Pareto 三选一 + 真实 badcase**，而不是一句"我建议降 30%"。

### 最佳回答（月薪30k工程师视角）

**一、成本建模：把公式展开到变量级**

```
C_turn = C_prompt + C_completion + C_embed + C_rerank + C_store + C_ops

C_prompt     = N_in × p_in
  N_context  = TOP_K_used × L_chunk(token)     # ← 本项目最大变量：3→10，成本 ×3
  N_history  = turns × avg_len_per_turn        # ← 第二大变量，多轮线性累加
C_completion = N_out × p_out
C_embed      = N_q_tokens × p_emb（写入摊销 ≈ 0）
C_rerank     = N_candidates × 单次前向成本     # ← 自托管时的隐形 CPU 大头
```

代入真实量级（国内常见价：输入 ¥2/百万、输出 ¥8/百万）：

| 项 | 量级（本系统） | 单次成本 |
|---|---|---|
| prompt | system 200 + history 300 + context（`RERANK_TOP_N=3` × 300 = 900；按 `TOP_K=10` 则 3000）+ query 50 ≈ **1.5k / 3.6k** | ¥0.003 / ¥0.007 |
| completion | ≈ 300 token | ¥0.0024 |
| embedding（查询侧） | ≈ 30 token | ≈ 0 |
| 重排（自托管） | 10 候选 × ~10ms CPU | 不占 token 预算，但占机器 |
| **单次合计** | | **≈ ¥0.006 ~ ¥0.010** |

10 万次/天 ≈ **¥600-1000/天**。

**结论：大头是 prompt（输入）侧。** 理由：① RAG 把外部知识重复塞进每次请求，输入量被 TOP_K 与历史轮数线性放大；② 输入是"每次重复付费"，而知识库是静态的；③ 输出只有几百 token 且可压。
但**大头会漂移**：开自托管重排后 `C_rerank` 变算力大头；遇到"详细介绍"类问题 completion 会翻盘。所以正确做法是**从 trace 里拉真实 token 分布（P50/P90/P99）算**，而不是拍脑袋。

**二、三种降本手段：对比与组合**

| 手段 | 典型收益 | 副作用与失效场景 | 缓解手段（关键） | 优先级 |
|---|---|---|---|---|
| **动态 TOP_K / 历史滑窗**（常被忽略的零成本手段） | 输入降 20-40% | 切掉的那条恰好是答案来源 → 召回下降 | 按检索分数自适应：达标就少塞；历史改滑窗 + 早期轮摘要 | **P0** |
| **语义缓存** | 头部命中 30-60%，直接省掉整条链路，延迟降到 ms 级 | ① 误命中（"怎么续借" vs "怎么取消续借"）② 知识更新后脏缓存 ③ 与稠密 embedding 不匹配 | 阈值**按意图分级**（FAQ 0.90；涉数值/时间 0.95 或禁用）；缓存绑定 `kb_version`，知识更新按 doc 失效；换稠密模型时同步换相似度算法 | **P1** |
| **模型分级路由** | 简单问题降本 60-80% | 路由误判 → 难题进小模型 → 长尾质量崩 | 路由依据用**意图 + 检索置信度 + 问题长度**（不要用一次 LLM 去判断，那是负收益）；低置信 → **升级大模型重答** | **P2** |
| **prompt/上下文压缩** | 输入降 30-60% | 压缩丢关键句 → 答案缺失或幻觉；摘要本身要花钱 | 先做"无损压缩"（去重、精简模板）；有损压缩（LLMLingua 类）必须 A/B | **P3（最后）** |

组合策略（这块最见功力）：

```
1. 无损优先：动态 TOP_K + 历史滑窗/摘要       → -25%，质量 ≈ 0 损失
2. 头部收割：语义缓存（分级阈值 + kb_version） → 头部再 -40%
3. 分层路由：简单意图走小模型 + 置信度升级兜底 → 全量再 -30%
4. 有损压缩：只在输入超长的长尾上开，A/B 验证后放量
```
再补两个常被忘的：**并发去重**（同一 query 并发只放一个回源）、**限长**（`max_tokens` + 提示简洁）。

**三、量化验证与长尾决策**

验证口径（三件事缺一不可）：

1. **质量分可校准**：rubric 化质量分 Q（事实正确性 / 依据充分 / 完整度 / 无害，分维度打分），judge 与人工一致率或 Cohen's κ > 0.8 才准用——**judge 未校准的评测结果不能作为决策依据**。
2. **分层评测集**：头部（Top 20 意图 × 30 条）+ 长尾（随机 200 条）+ 历史 badcase 50 条，**分层出分**。
3. **统计显著性**：对每条样本算 ΔQ，bootstrap 出 95% 置信区间。通过标准：
   - 整体 ΔQ 的 **CI 上界 < 3%**（不是点估计 < 3%）
   - 且**无任何单一分层下降 > 5%**
   - 且成本侧用真实 trace 的 token 分布核算达标

长尾掉 15%、头部掉 1%：**直接拒掉"平均只掉 3%"这个说法，不做全局切换。** 三个理由：① 长尾恰恰是高价值场景（复杂学科咨询、教师/研究生专库），头部问题用户自己查也行；② 投诉与口碑来自长尾；③ 长尾坏样本会回流进知识库与下一轮迭代，形成负反馈。

处置不是回滚，是**分层止损**：

- 头部（意图明确 + 检索置信度高）走降本链路；
- 长尾 / 未知意图 / 检索分数 < θ / 多轮未解决 → **强制走原链路**（全 TOP_K + 大模型）；
- 护栏：长尾分层质量分下降 > 5% 即自动回退该分层。

给业务方的沟通（**给选项，不给结论**）：

| 方案 | 成本 | 长尾质量 | 代价 |
|---|---|---|---|
| A（推荐） | -30% | -1% | 无，可立即全量 |
| B | -50% | -15% | 预计月投诉 +X 件，需业务方签字接受 |
| C | -50% | -2% | 需额外做长尾保护路由，工期 +2 周 |

并**附 5 条真实 badcase 的对比文本**。业务方看不懂"长尾 -15%"，但看得懂"这个用户问了 3 遍都没得到答案"——**拿具体错误说话比拿百分比有效十倍**。

**生产经验总结**：
1. **先量化再优化**：没有 trace 里的真实 token 分布，任何降本方案都是拍脑袋。
2. **语义缓存是收益最大、也最容易造成静默降质的手段**——必须绑定 `kb_version`，否则你修好了知识库，用户还在拿旧答案。
3. **降本必须按难度分层路由，不能全局切换**：全局切换等于用长尾质量补贴头部成本。
4. **给业务方 Pareto 选项 + badcase，不要给单点答案**：工程师的责任是把取舍摆清楚，不是替业务方拍板。

## 第 3 题：可观测性——RAG 系统到底该埋什么

**题目**：请说明 1）传统 APM 三件套（QPS / 延迟 / 错误率）**为什么对 RAG 系统不够用**？请给出 RAG 特有的**三层指标体系**（检索层 / 生成层 / 业务层）及每层的关键指标与告警阈值设计。 2）一次请求跨越：网关 → 限流 → 意图识别 → 检索 → 重排 → LLM → 落库。请设计**分布式链路追踪的 span 划分与关键 tag**，并说明拿到一条慢请求 trace 时，你**如何定位慢在哪一环**。 3）如何做**线上质量的实时监控**（无人工标注）？请给出 3 个可作为"质量代理指标"的线上信号，并说明它们各自的**误报风险**（什么情况下指标好看但体验很差）。

### 学员回答

**1）为什么 APM 三件套不够 + 三层指标**

传统 APM 只看 QPS、延迟、错误率，看不到答案质量。RAG 系统即使三个指标都正常，答案也可能是错的，所以还要关注检索质量和生成质量。

三层指标：
- 检索层：召回率、准确率、检索耗时
- 生成层：LLM 延迟、token 消耗、幻觉率
- 业务层：用户满意度、点踩率

告警阈值：召回率低于 90% 告警，延迟超过 3s 告警。

**2）链路追踪设计**

span 划分：gateway → rate_limit → intent → retrieve → rerank → llm → db。
tag：request_id、user_id、intent、耗时。

拿到慢请求 trace：看哪个 span 耗时最长，就是那一环慢。

**3）线上质量代理指标**

- 点踩率：用户点踩说明答案不好。
- 转人工率：用户不满意才会转人工。
- 答案长度：答案突然变短可能有问题。

误报风险：点踩可能是用户误触。

### 回答不足

1. **过于表面**：第 1 问的"为什么不够"只说了一句"看不到答案质量"，没点破本质：APM 测的是"**请求是否被正确处理**"，而 RAG 最致命的失败恰恰发生在系统完全正常时——检索到过时文档、答案脱离上下文、模型自信编造，**200 OK、延迟正常、零异常**。这个"静默降质"的命名与机制你没说出来。
2. **概念错误**：把**离线指标搬到了线上**。"召回率 < 90% 告警"在线上根本算不出来——线上没有标注，你不知道正确答案是哪篇文档。线上能算的是"Top1 相似度的 P10""空结果率""chunk 使用率"这类**无标注代理指标**。离线指标（召回率、NDCG、幻觉率）靠 golden set 回归，两者用途不同，混用是概念性错误。
3. **部分遗漏**：检索层漏了最能暴露问题的三个——**Top1 相似度分布**（P10 低 = 大量问题根本没检索到东西）、**空结果率**、**chunk 使用率**（进 prompt 的 chunk 有多少真被引用，低于 50% 说明在往 prompt 里塞垃圾）。生成层漏了**降级率**（本系统 `mode=template` 占比，这是最直接的健康信号）。业务层漏了**重复提问率**与**任务成功率**（承诺续借成功 ≠ 真续借成功）。另外阈值只有孤零零两个数字，没有给出"分位数 + 环比 + 分层"的设计原则。
4. **机制不清**："哪个 span 耗时最长就是哪一环慢"是错误方法论。第一步必须是算 **gap = 墙钟 − Σ(span self time)**：gap 大说明时间花在排队/事件循环阻塞/异步调度上，不是任何组件慢。跳过这步会在错误的地方优化。另外没提"**被放大**"（同一次请求 llm 被调 N 次、检索被拆多次），以及"生成太长"与"服务慢"的区分。
5. **过于表面**：tag 只有 request_id/user_id/intent/耗时，缺了复盘真正需要的：`model`/`embedding_model`/`reranker`、`kb_version`/`index_version`、`prompt_tokens`/`completion_tokens`/`cost`、`retrieved_doc_ids`/`chunk_ids`/`scores`、`cache_hit`、`degraded`、`error_type`。没有这些，事后只能说"慢了"，说不出"为什么慢"。
6. **缺少层次**：第 3 问把"答案长度"当质量指标是错的（长度变化可能只是知识库更新），应换成**答案分布漂移**（长度 + 模板化措辞 + 拒答率 + 与上下文相似度的**分布** PSI）。而且"误报风险"只写了"可能误触"，没有给出**交叉验证**方法——这才是真正考点：任何单一代理指标都会被"更自信地胡说"骗过。

### 最佳回答（月薪30k工程师视角）

**一、为什么三件套不够，以及三层指标体系**

本质区别：QPS/延迟/错误率回答的是"**系统是否正常工作**"，而 RAG 最致命的失败发生在系统完全正常时。三个信号对这种"静默降质"完全无感。所以 RAG 的指标体系必须额外回答两个问题："**检索到对的了吗**"和"**答案站得住吗**"。

| 层 | 关键指标 | 为什么是它 | 阈值示例 |
|---|---|---|---|
| **检索层** | Top-K 命中率（离线/有标注） | 决定答案上限 | 日环比 -5pt |
| | **Top1 相似度 P10 / P50** | 线上无标注可用；P10 低 = 大量问题没检索到东西 | P10 < 0.6 |
| | **空结果率** | 用户直接得到"没找到" | > 5% |
| | **chunk 使用率**（被答案引用 / 进 prompt 总数） | 低于一半 = 在往 prompt 塞垃圾，又贵又干扰 | < 50% |
| | 索引新鲜度、检索 P99 | 知识过期 / 性能 | > 24h / > 200ms |
| **生成层** | TTFT、token 吞吐、P99 延迟 | 体验与容量 | P99 > 3s |
| | **降级率**（`mode=template` 占比） | 本系统最直接的健康信号 | > 20% |
| | **拒答率** | 静默降质的早期信号 | > 10% |
| | **忠实度 / groundedness** | 答案是否脱离上下文 | 均值 < 0.8 |
| | `completion_tokens` 分布、重试率、错误分类 | 成本与上游健康 | 重试率 > 5% |
| **业务层** | 点踩率、转人工率、**重复提问率** | 用户用脚投票 | > 3% / > 5% / > 8% |
| | **任务成功率**（续借/预约真完成，而非只承诺） | 唯一真正的业务结果 | 跌 > 5pt |
| | 平均解决轮数、未知意图占比 | 效率与意图覆盖 | — |

阈值三原则：**看分位数不看均值**（均值会被头部问题淹没）、**看环比/同比**（绝对值随业务波动）、**分层下钻**（按意图/用户群/实例）。每条告警配 runbook，否则就是噪音。

**二、span 划分、tag 与慢请求定位**

```
gateway (http.server)
├─ ratelimit ─ auth ─ session.load
├─ intent.classify ─ query.rewrite
├─ rag.retrieve
│   ├─ embedding.query
│   ├─ vector.search
│   └─ rerank
├─ prompt.build
├─ llm.generate
├─ postprocess（格式校验 / 事实校验）
└─ persist（mysql + redis）
```

必埋 tag（"能回答为什么"的最小集）：

```python
with tracer.start_as_current_span("llm.generate") as span:
    span.set_attributes({
        "model": settings.LLM_MODEL,
        "kb_version": kb_version, "index_version": index_version,
        "intent": intent, "route": "rag", "cache_hit": cache_hit,
        "prompt_tokens": n_in, "completion_tokens": n_out, "cost": cost,
        "topk": settings.TOP_K, "rerank_top_n": settings.RERANK_TOP_N,
        "retrieved_doc_ids": ",".join(doc_ids), "top1_score": top1,
        "degraded": mode == "template", "error_type": "",  # 429/5xx/timeout
    })
```

慢 trace 四步定位（**顺序不能变**）：

1. **先算 gap**：`gap = 墙钟 − Σ(span self time)`。gap 大 → 时间在排队/事件循环阻塞/GC/异步调度上，压根不是组件慢。这步能避免 80% 的错误归因。
2. **再看 self time 最大的 span**：精确定位组件。
3. **查是否被放大**：`llm.generate` 被调用几次（重试/多轮/工具调用）？`vector.search` 是不是被拆成多次？总延迟高可能是次数多，不是单次慢。
4. **区分"慢"和"长"**：看 `completion_tokens`——token 数异常大 = "生成太长"（提示词/业务问题），不是"服务慢"（容量问题）。再对比同 intent 的历史 P50：整体慢才是组件问题。

**三、3 个无标注质量代理指标与各自的骗术**

| 代理指标 | 怎么算 | 什么时候"指标好看但体验很差" | 防骗手段 |
|---|---|---|---|
| **① 忠实度 / 依据率** | 答案拆成断言，用小 NLI 模型判每条是否被进 prompt 的 chunk 支持，取最小值 | **上下文本身就是错的**——污染/过期文档让模型"忠实地"复述错误答案，忠实度满分但答案全错 | 与检索层信号交叉：忠实度高 **且** Top1 分低 **且** 来源是过期/低权威文档 → 判可疑 |
| **② 用户行为信号**（点踩、重复提问、转人工、复制后立即离开） | 按意图分层统计 | 点踩基数极低（用户懒得点）→ 噪声大；"答非所问但用户客气"不点踩；重复提问也可能只是想确认细节 | 设最小样本量；分层看；多信号**联合**判定（点踩↑ 且 轮数↑ = 真坏） |
| **③ 答案分布漂移**（长度 / 模板化措辞 / 拒答率 / 与上下文相似度 / embedding 聚类的 PSI） | 与上一周期分布比 PSI | 知识库正常更新也会漂移；"与上下文相似度高"可能是模型在**照抄不相关段落**——看着忠实，实则答非所问 | 漂移告警只做"提示"不下结论；配合人工抽样复核 |

共同的防骗原则（最重要的部分）：

- **单一代理指标一定会被骗过**，必须多指标交叉验证；
- **每天 50 条人工标注是代理指标的校准锚点**——定期算"代理指标分 vs 人工分"的相关性，相关性掉了说明代理指标已失效，要换；
- 保留 golden set 离线回归，作为代理指标失灵时的最后防线。

**生产经验总结**：
1. **埋点第一原则是"能回答为什么"**——`doc_id`/`score`/`kb_version`/`tokens` 少一个，事后就只能猜。
2. **线上不能算召回率**：把离线指标搬到线上是概念错误。
3. **慢请求先看 gap 再看 span**，跳过 gap 会在错误的地方优化。
4. **代理指标只能当线索不能当结论**，必须被人工锚点持续校准。

## 第 4 题：容量规划与压测

**题目**：请说明 1）目标 **200 QPS、P99 ≤ 3s**。请把这个目标**拆解到各组件**（FastAPI / MySQL / Redis / 向量库 / Embedding 服务 / LLM），给出每层容量估算方法与**瓶颈预判**（你认为最先崩的是哪个，为什么）？ 2）RAG 系统的压测与常规 Web 压测**有何本质不同**？请设计压测方案，重点说明：**如何构造有代表性的压测语料**、**如何避免压测打爆上游 LLM 配额或烧穿预算**。 3）压测发现瓶颈在 **Embedding 服务（CPU 密集）**。请给出 3 种扩容/优化手段（批处理、模型蒸馏/量化、GPU 化、缓存）及其权衡，并说明**如何验证优化真的生效**（而不是"看起来快了"）。

### 学员回答

**1）200 QPS、P99 ≤ 3s 的容量拆解**

- FastAPI：单机大概能扛 500 QPS，200 QPS 一台就够了，配两台做高可用。
- MySQL：主要存会话和消息，200 QPS 下压力不大，一台够用。
- Redis：性能很高，单实例足够。
- 向量库：知识库不大，几千 chunk，内存放得下。
- Embedding：每条 query 都要算向量，有点压力，多加几台。
- LLM：调外部 API，受配额限制，可能要提高配额。

最先崩的应该是 **LLM**，因为它最慢而且有配额限制。

**2）RAG 压测的不同与方案**

不同点：RAG 要调 LLM，每次调用都花钱，不能无限压。

压测语料：随机生成一批问题，或者用 ChatGPT 生成一些图书馆相关的问题。
避免烧钱：压测时间不要太长，控制请求量；可以用便宜一点的模型。

**3）Embedding 是瓶颈的优化手段**

- 批处理：多条 query 一起送进模型，提高吞吐。
- 模型量化：量化成 int8，速度更快。
- 缓存：把算过的 query 向量缓存起来。

验证：压测看 QPS 提升多少、延迟降低多少。

### 回答不足

1. **缺少层次**：容量拆解全是"一台够用/多加几台"的直觉结论，**没有估算方法**。正确做法是"单请求资源消耗 × 目标 QPS → 所需资源"，再用 Little's law 反推并发（200 QPS × 3s = **600 并发在途**），最后留 30-50% headroom。没有方法论的数字等于没答。另外漏了**连接池**这个真瓶颈：`pool_size × 实例数 ≤ MySQL max_connections`，Web 层还没崩，连接池先崩。
2. **判断自相矛盾**：第 1 问说瓶颈是 LLM，第 3 问又说瓶颈在 Embedding（虽然那是题目给的）。真实情况是**两者都是瓶颈候选，但先崩的往往是自托管 Embedding/重排**——它是 CPU 密集且**同步跑在 FastAPI 事件循环里**（`rag_service.retrieve` 是同步调用），会同时把 QPS 压住和 P99 打爆，而且表现为"CPU 看起来不高"。LLM 的问题是延迟最大且**不可水平扩容**（受 RPM/TPM 配额）。这两条要一起说，并讲清"不可扩容"和"阻塞事件循环"是不同的失效机制。
3. **部分遗漏**：没做**延迟预算拆解**。P99 ≤ 3s 是总额度，必须先分配到各段，压测出来 3.5s 才知道该砍谁。不做预算，优化就是瞎撞。
4. **事实错误（最严重）**：语料"随机生成或用 ChatGPT 编一批图书馆问题"是错的。随机 query 的检索行为（向量分布、命中率、候选数）与真实分布差很远，压出来的数字没有参考价值，甚至会得出"容量很充裕"的假结论。
5. **过于表面**："避免烧钱：时间短一点、用便宜模型"不是工程方案。缺了五件套：影子/录制回放（VCR mock）、LLM mock server（固定延迟与 token 数，控制变量）、**Budget Guard**（脚本内置预算闸门自动停）、独立 API Key + 配额上限、爬坡而非瞬时打满。
6. **缺少层次**：验证只看 QPS 和延迟是"看起来快了"的典型。缺：① 分离变量；② **看分布 + 置信区间**（P99 单点抖动极大，800ms→700ms 可能只是噪声）；③ **端到端视角**（组件快了但端到端没快 = 瓶颈转移，Amdahl）；④ **质量不回退**（golden set 测 Recall@K/NDCG）；⑤ 资源视角（吞吐/核是否真提升）。

### 最佳回答（月薪30k工程师视角）

**一、200 QPS / P99 ≤ 3s 的拆解**

方法：单请求资源消耗 × 目标 QPS → 所需资源；Little's law 反推并发（200 × 3s = **600 并发在途**）；留 30-50% headroom。

| 组件 | 估算方法 | 结论 |
|---|---|---|
| FastAPI (uvicorn) | IO 密集单机 300-800 有效 QPS（前提：事件循环不被 CPU 密集代码阻塞） | 4-6 台 4C8G（含 headroom + 1 台容错） |
| MySQL | 每请求 2-5 次简单查询 → 400-1000 QPS；**真瓶颈是连接池** | 1 主 1 从够；`pool_size × 实例数 ≤ max_connections` |
| Redis | O(1) 操作 10 万+ QPS | 单实例足够，注意 big key / 热 key |
| 向量库 | 本系统几千 chunk，内存型毫秒级；百万级才需分片 | 单机内存索引足够 |
| Embedding（自托管） | bge 单条 ~10-20ms/核 → 200 QPS × 15ms = **3 核·秒/秒** | **瓶颈候选 ①**：CPU 密集 + 同步 + 进程内 |
| 重排（cross-encoder） | 10 候选 × ~10ms = 100ms/请求，纯 CPU | **瓶颈候选 ①'**：开 `RERANKER_ENABLED` 后是隐形 CPU 大户 |
| LLM | 外部 SaaS，受 RPM/TPM 配额；P99 2-8s | **瓶颈候选 ②**：延迟最大且**不可水平扩容** |

**预判最先崩的是自托管 Embedding/重排，其次才是 LLM 配额**，绝不是 FastAPI/MySQL/Redis。理由：① Embedding/重排是 CPU 密集且**跑在进程内**（`rag_service.retrieve` 同步调用），阻塞事件循环会让 QPS 上不去、P99 爆炸，而 CPU 使用率看起来"正常"——这是第 1 题"一切正常但 P99 暴涨"的同一个剧本；② LLM 吃掉 3s 预算的大头且受配额硬限制，没有扩容自由度。

**延迟预算（P99 3s 怎么分）**：

```
网关+鉴权 50ms | 意图+改写 100ms | embedding+检索 100ms | 重排 150ms
LLM 1800ms（TTFT 800ms + 生成 1000ms） | 落库 50ms
= 2.25s，余 750ms buffer
```
这意味着 **LLM 的 P99 一旦超过 2.5s，目标必挂**——所以必须靠流式（降低 TTFT 的体验影响）+ 超时 + 降级兜底，而不是指望优化检索省出的 100ms。

**二、RAG 压测的三大不同与方案**

与常规 Web 压测的本质区别：

1. **成本不对称**：每请求真花钱、有配额，不能"打满为止"。
2. **延迟重尾且由外部决定**：LLM 的 P99 与输入长度强相关，方差极大；必须把"我方耗时"与"上游耗时"分开统计。
3. **质量会随负载变化**（最关键）：Web 压测只问"能不能扛住"，RAG 压测还要问"**扛住以后答案还准不准**"——超时降级、缓存命中、并发限流都会改变答案质量。压测必须**同时采集质量指标**。

语料构造（压测成败的关键）：

- **来源**：生产日志按**意图分层采样** + 脱敏，按真实分布配比（头部 70% / 长尾 30%）。**不要随机生成、不要让 LLM 编问题**。
- **分层维度**：短问（5 字）、带上下文的追问、超长问题；外加 5-10% 脏输入（空串、超长、提示注入、乱码）。
- **必须含多轮会话脚本**：只压单轮会漏掉 history 膨胀带来的 token 与延迟增长。
- **版本化固化**成 golden corpus，历次压测可比。

防烧钱五件套：

```
1. 影子/录制回放（VCR）：线上录制的 LLM 响应做 mock，真实调用只在校准阶段少量发生
2. LLM mock server：固定 token 数与固定延迟 → 控制变量；单链路压测单独探配额上限
3. Budget Guard：脚本内置预算闸门，累计费用/请求数超阈值自动停止
4. 独立 API Key + 配额上限；爬坡 10→50→100→200，绝不瞬时打满
5. 缓存全关 + 向量预计算（embedding 只算一次）
```
执行顺序：单组件基准（embedding/检索/重排）→ 全链路（LLM mock）→ 小流量真实 LLM 校准。每档稳定 5-10 分钟，同时观察性能指标与质量指标（拒答率、降级率、忠实度抽样）。

**三、Embedding 瓶颈的三种优化与验证**

| 手段 | 做法 | 收益 | 代价与权衡 |
|---|---|---|---|
| **批处理** | 攒 8-32 条一起推理（本项目 `embed_batch` 已有）；线上用微批（10ms 时间窗） | CPU 下 2-5×，GPU 下 10×+ | 引入排队延迟；需要 batch scheduler |
| **蒸馏 / 量化** | bge-large → bge-small；ONNX + INT8 | 3-10× 加速，内存降 4× | **召回率会掉**（Recall@10 通常 -2~5pt），必须实测 |
| **GPU 化** | T4/A10 + 大 batch | 吞吐再翻 10× | 成本与运维复杂度；**QPS 不够时反而亏**（喂不饱 GPU） |
| **查询级缓存** | 归一化 query → 向量缓存 | 直接省 30-60% 计算（图书馆问题重复度高） | 只对重复 query 有效；要防击穿/雪崩 |

**顺序结论**：先做**批处理 + 查询缓存**（零质量损失）→ 再考虑**量化**（要测召回）→ 最后才 GPU。200 QPS 这个量级，把 CPU 批处理跑满通常就够了，上 GPU 大概率不划算。

如何验证"真的生效"（不是看起来快了）：

1. **分离变量**：只改一个变量，其他（语料、并发、机器规格）全固定；用**同一份 corpus 与同一条 query 序列**重跑。
2. **看分布 + 置信区间**：对比 P50/P90/P99 与完整延迟直方图，样本量 > 1e4，用 bootstrap 给 P99 置信区间——**800ms→700ms 很可能只是噪声**。
3. **端到端 + 组件双视角**：组件耗时降了但端到端 P99 没降 → 瓶颈已转移（Amdahl），要重新定位。
4. **质量不回退**：固定 golden set 测 Recall@K / NDCG@10，要求降幅 < 1pt。做不到这点，那不叫优化，叫偷工减料。
5. **资源视角**：看"吞吐/核"是否真提升，否则只是把排队从 A 挪到了 B。

**生产经验总结**：
1. **压测前先算钱**——没算过预算的压测会以一张账单收场。
2. **语料必须来自真实分布**，编出来的语料压出的数字是自欺欺人。
3. **"优化生效" = 分位数 + 置信区间 + 质量不回退**三者同时满足。
4. **先做免费的无损优化**（批处理、缓存、动态 TOP_K），再碰有损手段。

## 第 5 题：跨系统数据一致性（第 1 次拷问第 3 题的进阶）

**题目**：请说明 1）一次"续借"要写四处：业务系统（借阅记录）、MySQL（消息表）、Redis（会话历史）、积分/通知。请说明你会采用**什么一致性模式**（分布式事务 / Saga / 本地消息表 / 事务性发件箱），并**论证为什么不用强一致**？ 2）若"写业务系统成功、写 MySQL 消息表失败"，用户会看到什么？请设计你的**补偿与对账机制**，并说明如何保证"**用户看到的**"与"**实际发生的**"永远一致（提示：这是第 1 次拷问里"静默 no-op"危害的根源）。 3）**知识库（离线）与业务系统（实时）会给出冲突答案**——例如知识库说"3楼A区有《三体》"，但实时馆藏接口说已全部借出。**以谁为准**？你如何在架构上保证"**实时数据永远优先于知识库**"，且不让 LLM 有机会用过期知识覆盖实时数据？

### 学员回答

**1）一致性模式选型**

我会用**本地消息表**（事务性发件箱）：在 MySQL 里建一张 outbox 表，业务数据写入和消息写入放同一个本地事务里，然后由一个后台任务轮询 outbox 表去投递，失败就重试。

不用强一致（2PC/XA）的原因：2PC 性能差，要锁资源，而且协调者挂了会有悬挂事务。分布式事务实现复杂，我们这个场景可以接受短暂的不一致。

**2）写业务成功、写消息表失败**

用户会看到"续借失败"或者错误提示，但实际上书已经续借成功了，用户可能会再点一次导致重复续借。

补偿机制：写消息表失败就重试几次；重试还失败就记录日志并告警，让人工处理。
保证用户看到的和实际发生的一致：写入之前先查一次实际状态，返回前也再确认一次。

**3）知识库 vs 实时数据**

以**实时数据**为准，因为知识库是静态的，可能过期。

架构上保证：在 prompt 里明确写"以实时接口返回的数据为准，不要用知识库里的馆藏信息"；并且查询馆藏时优先调用实时接口，把结果放进 prompt 里。

### 回答不足

1. **论证不充分（最关键）**：第 1 问"为什么不用强一致"只说了"性能差、实现复杂、协调者单点"，全是教科书上的通用缺点，**没有结合本题场景给出致命理由**。真正的硬伤是：四处写入里有**外部业务系统**（借阅、积分/通知），它们几乎不可能支持 XA 协议——**2PC 在这里物理上做不到**。其次才是锁持有时间 = 最慢参与方的 RT（外部系统可能秒级），会把连接池打满。第一条是"做不到"，第二条才是"不划算"，你只答了后者。
2. **概念混淆**：把"本地消息表"当成完整方案，但它只解决"本地事务 → 可靠投递"，解决不了"**已成功的业务需要撤销**"（续借成功但积分扣减失败要回滚借阅）。完整方案必须是 **Outbox（保证事件可靠发出）+ Saga（提供每步的补偿动作）** 组合，你漏了 Saga 与补偿语义，也没提**幂等键**（`renewal_id + step`）与**指数退避 + 抖动**。
3. **过于表面**：第 2 问的补偿只有"重试 + 告警 + 人工"，**漏了对账**。重试会失败、会丢、会超时，唯一能保证最终一致的是**对账 job**：① 正向扫描停留超时的中间态；② 反向从业务系统拉流水与本库比对，发现"业务有本地无"（漏记）与"本地成功业务无"（幽灵）。没有对账就不叫最终一致，叫"祈祷"。
4. **部分遗漏**：没有识别这种失败的**真正性质**——业务已生效但系统告知失败，是"静默 no-op"的**镜像**：静默 success。也没给出根治办法：**先落意图（renewal_id, INIT）再执行，用户看到的是状态机的状态而不是一次 RPC 的成败**，以及"读时校验"（展示前回查业务系统真实状态）。只说"返回前再确认一次"，没说清这是架构原则还是临时补丁。
5. **机制不清（第 3 问）**：把"实时优先"寄托在 **prompt 里写一句话**，这是最典型的错误。LLM 在上下文里存在"3 楼 A 区有《三体》"这句话时，即使你写了"以实时为准"，它仍会倾向引用它。真正的防线有四道，且**最关键的在检索层**（事实类意图根本不检索知识库），你只答了最不可靠的那一道（提示词层）。
6. **场景缺失**：没提**数据侧治理**——知识库不应存"实时状态"字段，入库流水线要检测并拒绝/标记 volatile 字段；也没提**生成后的事实校验**（抽取答案里的书名/索书号/在架状态与实时数据比对，不一致则拦截重写）。

### 最佳回答（月薪30k工程师视角）

**一、选型：Outbox + Saga，以及为什么强一致是伪命题**

先说**为什么 2PC/XA 用不了**（按杀伤力排序）：

1. **物理上做不到**：四处写入包含外部业务系统与积分/通知服务，它们几乎不可能支持 XA 的 prepare/commit 协议。2PC 要求**所有**参与方支持，一个不支持就全盘否决——这不是"不想用"，是"没得用"。
2. **锁持有时间不可接受**：2PC 的锁时长 = 最慢参与方 RT，而最慢的是外部业务系统（可能秒级），会直接把你的连接池打满。
3. **协调者单点**：协调者挂掉产生悬挂事务，需要人工介入——你要的是自动化，不是新的故障源。
4. **收益不对等**：续借这种操作用户能接受"处理中"，要的是**最终一致 + 用户可见状态正确**，不是毫秒级强一致。

所以选型是 **本地消息表（Transactional Outbox）+ Saga 补偿**：

- **Outbox** 负责"必须发生的事"（写消息、发通知、加积分）：业务数据与 outbox 消息在**同一个本地事务**里写，独立 relay 进程轮询投递，失败重试 + 幂等 + 死信。
- **Saga** 负责"可撤销的事"（借阅记录、扣积分）：每步配正向操作与补偿操作（还书/退积分）；本场景步骤少且要求可观测，用**编排式（orchestration）**优于协同式（choreography）。
- **幂等**：每步带 `idempotency_key = renewal_id + step`，下游去重表；重试指数退避 + 抖动。
- **目标**：最终一致窗口 < 5s（用户刷新可见），> 60s 进人工对账。

```python
# Outbox：业务与消息在同一本地事务
with db.begin():
    db.execute("UPDATE borrow SET due_date=%s WHERE id=%s", (new_due, bid))
    db.execute(
        "INSERT INTO outbox(id, aggregate_id, event_type, payload, status) "
        "VALUES (%s,%s,%s,%s,'NEW')",
        (uuid4(), renewal_id, "RENEWAL_DONE", json.dumps({"bid": bid})),
    )
# relay 进程：轮询投递，下游按 idempotency_key 去重（不依赖事务）
```

**二、"写业务成功、写消息表失败"：静默 success 与对账**

先定性：这是"静默 no-op"的**镜像**——书确实续借了，但系统告诉用户"失败"。用户会再点一次（重复续借），或去柜台投诉"我明明续成功了"。这比 no-op 更糟，因为**用户有证据**。

根治原则：**用户看到的必须来自"唯一事实源的读"，而不是"我刚刚写成功了吗"的返回。**

1. **先落意图再执行**：进入 Saga 前先把 `renewal_id`（`INIT`）落库并返回"受理中"，前端轮询/推送最终状态。用户永远看到状态机的状态，而非一次 RPC 的成败。
2. **状态机**：`INIT → BIZ_DONE → MSG_DONE → DONE`，任一步失败进入 `COMPENSATING / COMPENSATED / FAILED_MANUAL`。
3. **补偿语义（关键判断）**：消息表写失败时**不回滚业务**——书确实续借了，回滚会直接造成用户逾期；正确处置是转为异步补偿 + 告警 + 人工，同时把用户可见状态设为"续借已成功（通知可能延迟）"。**补偿方向要按业务后果选，不是机械回滚。**
4. **对账 job（唯一能保证最终一致的手段）**：
   - 正向：扫描停留超 N 分钟的 `INIT`/`SAGA` 进行中 → 续跑或补偿；
   - 反向：从业务系统拉 T 时窗内的续借流水，与本库比对 → 发现"业务有本地无"（漏记，补写）与"本地成功业务无"（幽灵，撤回并通知用户）；
   - 对账结果进监控，未对平数量 > 0 即告警。
5. **读时校验**：所有面向用户的状态展示走 read-through，展示前回查业务系统真实状态。

**三、实时 vs 知识库：四道防线**

先立原则：**知识库负责"规则"（怎么借、几点关门、罚金多少），业务系统负责"事实"（这本书在不在、你借了几本）**。事实类问题的答案里，知识库根本不该出现。

| 防线 | 位置 | 做法 | 可靠性 |
|---|---|---|---|
| **① 召回层（最关键）** | 意图路由 | 识别"馆藏查询/是否在架/我的借阅"等事实意图 → 走 Function Calling 调实时接口，把结果作为**结构化事实**注入 prompt，**不检索知识库** | 高 |
| **② 数据层** | 入库流水线 | 知识库不存实时状态字段；用规则/NLP 检测"库存/在架/剩余"等易腐字段 → 拒绝入库或打 `volatile` 标记 + 短 TTL | 高 |
| **③ 生成层** | prompt | 显式分区与优先级："【实时数据】由接口提供，最高优先级；【知识库】仅提供规则说明；冲突以实时为准，且禁止使用知识库中的馆藏/库存/状态信息" | 中（单独用不可靠） |
| **④ 校验层** | 生成后 | 抽取答案中的事实断言（书名/索书号/在架状态/日期/数量）与实时数据比对，不一致 → 拦截重写或改兜底"以实时接口为准" | 高 |

```python
if intent in FACT_INTENTS:            # ① 事实类意图：不检索知识库
    facts = await library_api.query(slots)
    docs, mode = [], "realtime"       # 知识库内容不进入上下文
else:
    docs = retriever.retrieve(q)      # 规则类意图才走 RAG
answer = await llm.chat(build_messages(q, docs, facts=facts))
if violated := fact_check(answer, facts):   # ④ 生成后校验

```

**反例警告**：不要指望在 prompt 里加一句"请以实时数据为准"就够了。上下文里存在"3 楼 A 区有《三体》"这句话时，模型有强烈的引用倾向。**必须在召回层就不给它这个机会。**

**生产经验总结**：
1. **跨系统一致性靠对账，不靠重试**——重试会失败、会丢、会超时，对账才是唯一闭环。
2. **用户看到的状态来自状态机 + 读时校验**，不是来自某次写入的返回值。
3. **补偿方向按业务后果选**：会造成用户损失的"成功"不能机械回滚。
4. **实时优先要在召回层实现，不能只在提示词层祈祷。**

## 第 6 题：灰度发布与实验（Prompt / 模型 / 检索策略）

**题目**：请说明 1）**Prompt 改动如何安全灰度**？请设计实验方案：如何分流、**如何保证同一用户体验一致**、观测哪些指标、观察多久算"通过"、如何自动回滚？ 2）同时灰度"**新 Embedding 模型**"和"**新 Prompt**"会有什么问题？请说明**多变量实验的相互干扰**与解决方案（正交实验 / 逐变量 / 分层实验），并指出哪种组合**绝对不能同时灰度**（提示：换 Embedding 模型需要重建索引）。 3）线上 AB 显示：新策略的**"用户满意度"上升，但"平均对话轮数"也上升了**。这个组合说明什么？你如何判断**该不该全量**？还需要补看哪些指标才能下结论？

### 学员回答

**1）Prompt 灰度方案**

分流：按 user_id 哈希取模，比如 10% 的用户进实验组。
体验一致：同一个用户始终算出来同一个分组就行。
观测指标：准确率、点踩率、延迟。
观察多久：观察一周差不多。
自动回滚：如果指标变差就回滚到旧版本。

**2）多变量干扰**

同时灰度新 embedding 和新 prompt 会有问题：效果好了不知道是谁的功劳。解决方案是分开做，先上一个再上另一个。绝对不能同时灰度的：换 embedding 模型需要重建索引，回滚成本高。

**3）满意度上升但轮数也上升**

说明用户更喜欢新的回答方式，愿意多聊，整体是好的。但轮数上升意味着成本上升，需要看一下成本。我觉得可以全量，但要监控成本。

### 回答不足

1. **机制不清**："按 user_id 哈希取模，同一个用户始终算出来同一个分组"——这只答对了分流单元，没答 **sticky 的实现**：分流结果必须**持久化**（写 Redis/cookie，key 带 `exp_id`），否则改哈希函数、改实验配置、扩缩容重分片都会让用户跳组，实验直接失效。也没提 prompt 必须**版本化**（`prompt_id + version + hash`）并随 trace 落库，禁止线上热改字符串——否则事后无法还原"这条样本用的是哪个 prompt"。
2. **缺少层次**：观测指标只给了准确率/点踩率/延迟，缺**护栏指标（guardrail）**的概念——错误率、P99、拒答率、成本这类"不管主指标多好，破了就回滚"的指标，且**护栏优先级高于主指标**。另外"自动回滚"没给触发条件（连续几个窗口、什么阈值）与实现方式（改配置即时生效，不能走发布流程）。
3. **事实错误（样本量）**："观察一周"是拍脑袋。正确做法是**样本量估算**：点踩率基线 3%，想检出 +1pt，α=0.05、power=0.8 → 每臂需要约 1.5-3 万次对话；同时**至少覆盖 2 个完整周循环**（图书馆有工作日/周末差异），两者取较大。另外没提**不能中途偷看（peeking）**导致假阳性，要用固定样本量或序贯检验（mSPRT）。
4. **部分遗漏**：多变量干扰只给了"串行"，没给**分层实验（不同 salt 的独立哈希层）**、**多臂全组合（A/B/C/D，可测交互项但样本量 ×4）**、**互斥域**三种方案及其权衡。也没说清"换 embedding 必须重建索引"带来的真正风险：新旧向量**分数不可比**，会污染任何依赖阈值的实验；回滚要再重建一次（小时级）。正确做法是**双索引双写**，回滚只切路由。
5. **判断错误（第 3 问）**："满意度上升说明整体是好的，可以全量"——这个结论下得太快。满意度↑ + 轮数↑ 至少有三种解释（真实提升 / 回答变啰嗦用户追问 / 靠烧钱换态度分），你只考虑了第一种。**必须补任务完成率**（是否真解决）、**首轮解决率**、**单会话成本**、**满意度分层与显著性**、**转人工率**，并给出"多条件同时满足才全量"的判定规则。
6. **场景缺失**：没提爬坡节奏（影子 → 1% → 5% → 20% → 50% → 100%，每档覆盖一个完整高峰）与 kill switch（一键切回）。

### 最佳回答（月薪30k工程师视角）

**一、Prompt 灰度方案**

| 要素 | 设计 | 为什么 |
|---|---|---|
| **分流单元** | `user_id`（或公共设备用 `device_id`）**一致性哈希分桶 0-99**，不是 request 哈希 | request 哈希会让同一用户每次拿到不同 prompt，体验撕裂且无法测"用户级"指标 |
| **Sticky** | 分流结果写入 Redis/cookie：`exp_assign:{exp_id}:{user_id} → bucket` | 改哈希函数/改配置/扩缩容时用户不跳组；改实验只改"桶→变体"映射 |
| **变量管理** | prompt 版本化（`prompt_id + version + hash`），随 trace 落库 | 任何样本都能还原"用的是哪个 prompt"；禁止线上热改字符串 |
| **指标** | 主指标：点踩率、转人工率、忠实度抽样、golden set 离线分<br>效率：平均轮数、TTFT、P99、成本/次<br>业务：任务成功率（真续借成功）<br>**护栏**：错误率、P99、拒答率、成本 | **护栏优先于主指标**：护栏破立即回滚，不管主指标多好 |
| **观察时长** | ① 样本量估算：基线点踩率 3%，检出力 +1pt，α=0.05、power=0.8 → 每臂 1.5-3 万次对话 ② 至少 2 个完整周循环（工作日/周末差异）③ 两者取较大 | "观察一周"是拍脑袋；样本不足的结论是噪声 |
| **统计纪律** | 固定样本量后再看，或序贯检验（mSPRT）；**禁止中途反复偷看** | peeking 会大幅抬高假阳性率 |
| **自动回滚** | 护栏指标连续 3 个 5min 窗口超阈值 → 自动切回对照 + 告警；改配置**即时生效**，不走发布流程；保留 kill switch | 回滚路径必须比发布路径快 |
| **节奏** | 影子跑 1-2 天 → 1% → 5% → 20% → 50% → 100%，每档至少覆盖一个完整高峰时段 | 高峰与低谷的用户行为不同 |

**二、多变量干扰与绝对不能同时灰度的组合**

问题：同时灰度新 embedding 和新 prompt，观测到的变化无法归因（是 A、B 还是 A×B 交互）。更糟的是**换 embedding 模型必须重建全量索引**——向量空间变了，新旧向量与分数**不可比**，且回滚要**再重建一次**（小时级）。

| 方案 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **逐变量（串行）** | 先上 A 稳定，再上 B | 变量少、求稳 | 周期翻倍，但最安全 |
| **正交/分层实验** | 流量分层：层 1 分 embedding（salt A），层 2 分 prompt（salt B），独立哈希 | 变量间交互弱、都想快速验证 | 需要足够流量；**交互项测不出来** |
| **多臂全组合** | 四臂：old+old / new+old / old+new / new+new | 想测交互项 | 每臂样本需求 ×4，流量不够就废 |
| **互斥域** | 强耦合变量放进同一互斥域，禁止跨层 | 强耦合变量 | 实验吞吐降低 |

**绝对不能同时灰度的组合**：

1. **换 embedding 模型 + 任何依赖向量分数的改动**（新 reranker、新相似度阈值、新 TOP_K 策略）——索引重建不可回滚、新旧分数不可比，会把阈值类实验的结论彻底污染。
2. **知识库大版本更新 + prompt/模型变更**——内容变了，无法归因。
3. **基础设施变更（扩缩容、换向量库）+ 任何实验**——延迟变化本身会影响用户行为。

实操建议：embedding 类实验用**双索引 + 双写**（新旧索引并存，按分桶路由），回滚只需切路由（毫秒级），而不是"重建同一份索引再回滚"。

**三、满意度↑ + 轮数↑ 怎么判**

这个组合有三种解释，含义完全不同：

1. **好的解释**：新策略更有帮助，用户愿意多问，而且多轮任务完成率也上升 → 真实提升。
2. **警惕的解释**：回答变啰嗦或每次只答一半，用户必须追问才能得到完整答案 → 满意度那 1 分是"态度分"，不是"解决问题分"。
3. **坏的解释**：新策略把用户引导进更长的流程（反复确认），最终解决了所以满意度高，但**一次解决率下降、成本翻倍**。

必须补看的指标：

- **任务完成率 / 一次解决率（最关键）**：轮数涨但完成率也涨 = 可接受；完成率没涨而轮数涨 = **退化**。
- **单会话成本**（token 总和/会话）：满意度提升如果是靠烧钱换的，要算 ROI。
- **轮数分布**（中位数 vs P90）：是否有一小撮会话被拖到 10 轮以上。
- **满意度分层 + 显著性**：按意图、按轮数分层，看 CI 是否跨 0。
- **护栏**：转人工率（下降才是真解决）、P99（多轮 = 更多请求）。
- **留存**：7 日回访率——满意度是即时主观分，留存是硬指标。

**决策规则**：满意度 CI 下界 > 0 **且** 任务完成率不降 **且** 单会话成本涨幅 < X% **且** 护栏不破 → 才可全量。否则**按意图分层发布**（在满意度提升明显、成本可控的意图上全量，其余回退）。

**生产经验总结**：
1. **分流要 sticky 且写进 trace**，否则实验数据不可复盘、用户会跳组。
2. **护栏指标优先于主指标**——主指标变好而护栏破了，一样回滚。
3. **换 embedding 用双索引双写，不要重建同一份索引**——回滚成本决定实验敢不敢做。
4. **满意度必须配任务完成率与成本一起看**，单看满意度一定被骗。

## 第 7 题：混沌工程与降级链路验证

**题目**：请说明 1）你在第 1 次拷问第 4 题设计了"LLM 503 → 降级 BM25 / FAQ 缓存"的链路，但**从未验证过它真的能用**。请设计一次**混沌演练**：注入哪些故障、如何注入（工具/方式）、预期表现是什么、**如何判定演练成功**？ 2）演练中发现：LLM 熔断后，**降级流量直接把 BM25 服务打挂了**——降级服务本身没做容量规划。这个**"降级反噬"**问题你怎么解决？降级链路本身需要满足什么设计要求？ 3）如何把混沌演练**常态化**（而不是一次性的运动）？请设计自动化演练的**节奏、爆炸半径控制、自动停止与回滚机制**，并说明如何让演练不影响真实用户。

### 学员回答

**1）混沌演练设计**

注入故障：把 LLM 服务停掉，或者让 LLM 接口返回 503。
注入方式：手动改代码让 LLM 调用失败，或者在测试环境把服务停掉。
预期表现：系统自动降级到 BM25 / FAQ 缓存，用户还能拿到答案。
判定成功：服务没挂，用户还能看到回答。

**2）降级反噬**

原因是 BM25 服务容量不够。解决：给 BM25 扩容，多部署几个实例。

降级链路的设计要求：要足够简单、要快、要有兜底。

**3）常态化**

每周五下午做一次演练，记录结果，有问题就修。控制爆炸半径：在测试环境做，不要影响用户。自动停止：出问题就手动停止。

### 回答不足

1. **缺少层次（第 1 问最致命）**：演练设计缺了最关键的一步——**先写假设（hypothesis）和可验证的成功判据**。你说"判定成功：服务没挂"，这不是判据，是事后感觉。正确写法是预先定义 SLO：用户侧错误率 < 1%、P99 < 1.5s、无 5xx 冒泡、**降级触发时间 < 30s、恢复时间 < 60s**、降级期间 sources 非空率 > 95%。没有预定义的判据，演练就只是"搞了一次破坏"。
2. **方式不安全**："手动改代码让 LLM 调用失败"是最不可控的注入方式——改代码意味着要走发布，回滚慢、易残留、无法精确控制比例，而且**改过的代码可能忘了改回来**。正确做法按安全等级排序：配置开关（`CHAOS_LLM_FAILURE_RATE`）> 网络层（Toxiproxy/服务网格 fault injection）> mock server > 改代码。
3. **部分遗漏**：注入清单只给了"LLM 503"一种。真实演练至少要覆盖：LLM 慢（TTFB 30s）、429 限流、连接池耗尽、Redis 宕机、向量库超时、MySQL 慢查询、embedding OOM、pod kill、网络分区、磁盘满。**只测一种故障等于没测**——因为你要验证的是"降级链路"这个机制，不是"这一个注入点"。
4. **过于表面（第 2 问）**："扩容多部署几个实例"只答了表象，没解释**为什么会反噬**。真正的机制是：降级后延迟大幅下降，由 Little's law（并发 = QPS × 延迟），单位时间内完成的请求更多 → **到达降级服务的 QPS 被放大**；而降级服务通常按低规格部署。所以解法有四条（容量对等 / 入口限流 + load shedding / 短超时 + 有界队列 / 降级分级），扩容只是其中一条。也没提**降级路径不应依赖另一个可能挂的服务**。
5. **概念不清**：降级链路的设计要求只写了"简单、快、有兜底"三个形容词，没有可检查的 checklist（无状态、依赖更少、独立超时与限流、可观测、可手动强制切换、**且降级本身要被演练覆盖**）。
6. **缺少层次（第 3 问）**："每周五下午做一次 + 手动停止"不是常态化机制。缺：① 分层节奏（CI 冒烟注入 / 每周单服务 / 每月 GameDay / 每季度机房级）；② 爆炸半径控制（环境分级、生产只打 1-5% 或影子流量、时间窗 + 演练任务 TTL、变更冻结期禁止）；③ **自动中止条件**（abort conditions 硬编码：用户错误率 > 2%、P99 > 3× 基线、业务成功率跌 > 10%）与**声明式恢复**（平台保证最终回到"无注入"状态，哪怕演练进程被杀）；④ 闭环（假设→结果→差距→改进项进缺陷跟踪，未闭环项下次优先复测）。

### 最佳回答（月薪30k工程师视角）

**一、一次 LLM 503 的混沌演练设计**

**先写假设**（这一步决定演练有没有价值）：

> 当 LLM 服务 5xx/超时率 > 50% 持续 30s 时，系统自动降级到模板/BM25 链路，对用户无感：用户侧错误率 < 1%、P99 < 1.5s、无 5xx 冒泡，且答案仍带来源引用。

**注入方式**（按安全等级从高到低）：

| 方式 | 做法 | 优点 |
|---|---|---|
| **配置开关（首选）** | 在 `LLMClient` 前加 chaos 中间件：`CHAOS_LLM_FAILURE_RATE=1.0` 按比例返回 503 / 延迟 30s / 连接重置 | 不碰上游、最安全、可随时关闭、可精确控比例 |
| **网络层** | Toxiproxy / iptables / 服务网格（Envoy 的 delay/abort）注入 latency、timeout、reset | 更接近真实网络故障 |
| **依赖层** | 把 `LLM_BASE_URL` 指向返回 503 的 mock server（WireMock） | 简单，适合 CI |
| **工具** | Chaos Mesh / Litmus（K8s）、pytest + monkeypatch（单测级） | 可编排 |

**注入清单**（至少覆盖这些，只测一种等于没测）：LLM 503、LLM 慢（TTFB 30s）、LLM 429、httpx 连接池耗尽、Redis 宕机、向量库超时、MySQL 慢查询、embedding OOM、pod kill、网络分区、磁盘满、索引缺失。

**成功判据（预先写成可验证的 SLO）**：

- 用户侧：错误率 < 1%、P99 < 1.5s、无 500 冒泡；
- 时效性：**降级触发 < 30s**（检测 + 生效），**恢复 < 60s**；
- 质量：降级期间 `sources` 非空率 > 95%，无编造（模板模式天然只拼检索内容）；
- 可观测：熔断状态、降级次数、降级原因在监控面板可见并告警；
- 无残留：演练后配置恢复、无脏缓存、无悬挂请求。

任一不满足 → 记 defect，定 owner 与期限，下次演练复测。

**二、降级反噬：为什么会发生，怎么解决**

**机制**：降级后单次延迟大幅下降，由 Little's law（并发 = QPS × 延迟），单位时间完成的请求增多 → **到达降级服务的 QPS 被放大**（原来被 LLM 慢挡住的并发现在全涌进来）。而降级服务（BM25/FAQ）通常按"低优先、小规格"部署 → 必然被打挂。本质是**降级路径从未按 100% 流量做过容量规划**。

四条解法：

1. **容量对等（最重要）**：降级链路必须按承接 100% 流量规划。更聪明的做法是让**降级路径比主路径更轻**——离线模板只做字符串拼装，CPU 消耗不到 LLM 链路的 1/10，本就该扛得住；真正的问题往往是 BM25 是独立服务且规格过小。
2. **入口限流 + load shedding**：降级触发时同步下调全局限流阈值（200 → 120 QPS），主动 shed 非核心流量（闲聊、非实时类）。**宁可 429 也不要全挂。**
3. **短超时 + 有界队列**：降级服务超时 300ms，队列满立即失败到第二级兜底（静态 FAQ / 引导人工）。
4. **降级分级而非单点**：主 LLM → 小模型 → 检索摘要模板 → 静态 FAQ → 引导人工，每级都更轻、更能扛，且都做过容量验证。

降级链路 checklist：① 无状态或状态可丢 ② **依赖更少**（降级路径不应依赖另一个可能挂的服务）③ 延迟更低、资源更省 ④ 独立超时与限流 ⑤ 可观测（降级率、降级原因、降级后质量）⑥ 可手动强制切换（演练用）⑦ **降级本身要被混沌演练覆盖**（元要求）。

**三、常态化机制**

**节奏分层**：

| 频率 | 内容 | 时长 |
|---|---|---|
| 每次发布前 | CI 里的 chaos 冒烟用例（阻断发布） | 5-10 min |
| 每周 | 随机选一个组件做单服务注入（低峰） | 10-30 min |
| 每月 | **GameDay**：组合故障 + 人工介入演练 | 半天 |
| 每季度 | 全链路 / 机房级演练 | 按演练计划 |

**爆炸半径控制**：

1. **环境分级**：测试/预发跑全量故障；生产只跑"已验证过、影响可控"的注入；
2. **流量隔离**：生产只对**影子流量**或 1-5% 真实流量（按 user_id 分桶）注入，或只对内部账号；
3. **时间窗**：限定低峰，演练任务带 **TTL**，超时强制停止；
4. **冻结期**：大促、变更冻结期禁止演练；
5. **宣告**：演练同步到值班群，避免被当成真事故。

**自动停止与回滚**：把中止条件**硬编码进演练平台**——用户侧错误率 > 2%、P99 > 3× 基线、业务成功率跌 > 10%、SLO burn rate 超阈值、人工一键 abort → 立即停止注入 + 恢复配置 + 回滚变更 + 通知。平台必须是**声明式**（描述期望的故障状态），保证即使演练进程被杀也会收敛回"无注入"状态。

**不影响真实用户的三种方式**：影子流量（mirror 一份真实请求到演练实例，在主链路旁边注入，用户看到的仍是主链路结果）、预发环境重放生产流量、生产小流量分桶 + 秒级回滚。

**闭环**：每次演练产出"假设 → 结果 → 差距 → 改进项"，进缺陷跟踪；未闭环项下次优先复测；已验证的降级路径写进 runbook 与值班手册。

**生产经验总结**：
1. **混沌演练的价值不在"搞崩系统"，在验证你写的降级代码真的能跑**——没演练过的降级等于没有降级。
2. **降级路径必须按 100% 流量做容量规划**，且要比主路径更轻。
3. **演练平台必须带 abort 条件与声明式恢复**，否则演练本身会变成事故。
4. **先注入配置开关，再注入网络，最后才动代码**——可控性决定演练敢不敢常态化。

## 第 8 题：知识治理与组织协作（从技术到流程）

**题目**：请说明 1）知识库由多部门共管（借阅规则归流通部、开放时间归办公室、数据库指引归技术部），出现**知识冲突与责任不清**时，技术上如何支撑（文档级归属与签核、冲突检测、生效与失效时间）？ 2）部分知识有**时效性**（寒暑假规则只在假期生效、临时闭馆通知只覆盖某几天）。你如何做**时间感知的知识检索**（按当前日期自动启用/停用文档）？请给出设计，并说明**边界情况**（跨假期的提问、规则过渡期、时区）。 3）馆员反馈"系统答错了"，但技术指标一切正常。你如何设计**用户反馈闭环**（点赞/点踩/纠错入口），把单点反馈转化为系统级改进？并说明**如何防止恶意或误触的反馈刷低知识库质量**。

### 学员回答

**1）多部门共管的技术支撑**

给每篇文档加 metadata，标记归属部门、负责人、状态。冲突检测：入库时检测是否有重复或冲突的内容，发现冲突就通知相关人员人工审核。生效与失效：加 `effective_from` 和 `effective_to` 字段。

**2）时间感知检索**

给文档加生效时间字段，检索时过滤掉不在有效期内的文档：
```sql
WHERE effective_from <= NOW() AND (effective_to IS NULL OR effective_to >= NOW())
```
临时闭馆通知设置成只在某几天生效。

**3）反馈闭环与防刷**

在每条答案下面加点赞/点踩按钮，用户点踩后可以填写原因。系统收集点踩数据，对点踩多的文档降低权重，严重的话自动下架。
防刷：限制同一用户在短时间内不能重复提交反馈。

### 回答不足

1. **过于表面（第 1 问）**："加 metadata 标记归属"只说了字段名字，没说**治理机制**——谁有权改（owner + review_cycle）、怎么改（PR 式签核流：知识即代码，front-matter + CI 校验必填字段 + 冲突检测 + 影响面预览）、改完怎么生效（增量重建受影响 chunk 而非全量重建）。也没提**权威等级**（办公室通知 > 部门 FAQ > 摘录），而这是自动裁决冲突的前提。
2. **机制不清**：冲突检测只说"检测重复或冲突，通知人工审核"，没说**怎么检测**。可用的手段至少三种：① 用 embedding 把问答对聚类，同一簇内答案不一致 → 标 conflict；② 对开放时间、罚金、借阅上限等**关键字段抽取成结构化槽位再比对**（比全文比对准得多）；③ 按权威等级自动提示覆盖方向。全靠人工审核在 200 篇规模就已不可行。
3. **部分遗漏（第 2 问）**：SQL 过滤写对了，但漏掉四个关键点：① **过滤必须发生在检索阶段而非入库阶段**（否则无法回溯"当时为什么这么答"）；② 临时通知要有 `priority` 加权置顶；③ 过渡期需要"双轨 + 显式生效日期标注"，不能硬选一条；④ **时区与"今天"的归一化**（必须用馆址本地时区，把"今天/周末"解析成具体日期）。
4. **判断错误（第 2 问最关键的坑）**：完全没意识到**"跨假期的提问"要用问题里的日期检索，而不是 `NOW()`**。用户 1 月 20 日问"3 月 1 日开放吗"，用 `NOW()` 过滤会返回寒假规则，一定答错。必须做**时间槽位抽取 + `as_of` 参数化检索**。这是时间感知检索里最难也最容易丢分的一条。
5. **自动闭环风险（第 3 问最严重）**："点踩多的文档降低权重，严重的话自动下架"——这是**未校准的自动闭环**，是第 2 次拷问点名的老问题复发。缺：① 阈值必须"多条独立用户 + 时间窗"双条件（如 7 天内 ≥5 个不同用户），**单次反馈绝不自动改权重**；② **不可逆操作（下架/删除）必须人工确认**，自动化的上限是"降权 + 建工单"；③ 角色权重（馆员 5 / 普通用户 1 / 匿名 0.1）；④ 监控反馈本身（点踩率突增检测，区分"被刷"与"真故障"）；⑤ 若用 LLM 判断反馈是否合理，必须先与人工标注对齐。
6. **机制不清**：反馈闭环缺了"**单点 → 系统级**"的转化机制——反馈落库必须绑定 `trace_id`/`doc_ids`/`chunk_ids`/`scores`/`model`/`prompt_version`/`kb_version`（无上下文就无法归因），且要**按 chunk 聚类而不是按问题聚类**（同一 chunk 被多次点踩才是系统信号）；以及**闭环验证**（修复后固化成回归用例，观察该 chunk 点踩率是否下降）。另外漏了缓存：`SemanticCache` 的 key 必须带日期/`kb_version`，否则修好了知识库用户还在拿旧答案。

### 最佳回答（月薪30k工程师视角）

**一、多部门共管的技术支撑**

**文档元数据（治理的最小集）**：

```yaml
---
doc_id: kb/borrow_rules.md
owner_department: 流通部        # 归属
owner_person: 张老师            # 责任人
review_cycle: 180d              # 复核周期
status: approved                # draft/pending/approved/deprecated
authority_level: 2              # 权威等级：办公室通知 3 > 部门FAQ 2 > 摘录 1
effective_from: 2026-01-01
effective_to: null
category: policy_doc
---
```

**签核流（推荐"知识即代码"）**：知识库用 Git 管理，变更走 PR：CI 校验必填 front-matter 字段 → 自动冲突检测 → 影响面预览（这次改动会影响哪些历史问题的答案）→ owner 审批合并 → **增量重建受影响 chunk**（不是全量重建）。这样签核、回滚、审计全部天然具备。

**冲突检测（入库时自动跑，三种手段）**：

1. **语义聚类**：把问答对做 embedding 聚类，相似度 > 0.9 的簇内若答案不一致 → 标 `conflict`，**阻断入库**并通知双方 owner；
2. **结构化槽位比对**：对开放时间、罚金、借阅上限等关键字段抽取成结构化槽位再比对——比全文相似度准得多，且能给出"哪里冲突"；
3. **权威等级提示**：高权威覆盖低权威，但**仍需人工确认**（自动裁决只给建议，不做决定）。

**生效与失效**：所有文档带时间窗与 `status`；**过滤发生在检索阶段**（`metadata_filter`）而非入库阶段，这样才能回溯"当时为什么这么答"。每个 chunk 带 `doc_id + version + 审批人`，答案的 `sources` 能一键跳到原文与审批记录。

**二、时间感知检索**

**两个时间维度**：文档的**业务有效期**（`effective_from/to`）+ 索引的**系统版本**（`ingested_at`）。检索按业务时间过滤。

```python
def retrieve_with_time(query: str, as_of: datetime | None = None):
    # 关键：as_of 来自「问题里的时间槽位」，不是 now()
    as_of = as_of or extract_time_slot(query) or now_local()
    return retriever.retrieve(
        query,
        metadata_filter={
            "status": "approved",
            "effective_from__lte": as_of,
            "effective_to__gte": as_of,     # NULL 视为永久有效
        },
        priority_boost={"urgent": 1.2},      # 临时通知加权置顶
    )
```

**边界情况清单（这是本题真正的分数所在）**：

| 边界 | 处理 |
|---|---|
| **跨假期的提问（最容易丢分）** | 用户 1/20 问"3 月 1 日开放吗" → 必须用**问题里的日期** `as_of` 检索，而不是 `NOW()`。要做时间槽位抽取，否则一定答错 |
| **规则过渡期** | 提前 7 天"双轨检索"：新旧规则都进 prompt，答案里显式标注生效日期，避免用户按旧规则行事 |
| **时区与"今天"** | 图书馆是本地业务，一律用**馆址本地时区**（Asia/Shanghai）而非 UTC；"今天/明天/周末"先归一化成具体日期再过滤；注意 23:59 跨天请求 |
| **临时闭馆粒度** | effective 要支持到小时/分钟（"下午闭馆"） |
| **答案可追溯** | 答案必须带"截至 X 月 X 日"的时间戳与有效期说明，避免用户拿旧截图当依据 |
| **缓存** | `SemanticCache` 的 key 必须带**日期 / `kb_version`**，否则昨天缓存的开放时间今天还在用 |

**三、反馈闭环与防刷**

**入口**：点赞/点踩 + 一键纠错（选项化：事实错误 / 过期 / 答非所问 / 不完整 / 不礼貌）+ 转人工。

**单点 → 系统级的转化路径**：

1. **反馈必须绑定完整上下文**：`trace_id`、`query`、`doc_ids`/`chunk_ids`、`scores`、`model`/`prompt_version`、`kb_version`、时间。没有这些无法归因。
2. **按 chunk 聚类，不是按问题聚类**：同一 chunk 被多次点踩 → 该 chunk 可疑。这是把单点反馈变成系统信号的关键。
3. **分级处置**：① 高频高置信（同一 chunk 7 天内 ≥5 次点踩）→ 自动生成工单给 owner + 临时降权；② 中频 → 人工复核队列（馆员每周处理）；③ 低频 → 记录，作为评测集补充样本。
4. **闭环验证**：修复后把该 case 固化成回归用例，重跑验证，并观察该 chunk 点踩率是否下降。

**防刷（五道闸门）**：

```
1. 身份与去重：登录用户才计权（公共设备用设备+会话指纹）；同一用户对同一答案只计一次
2. 频率上限：单用户单位时间反馈数超阈值 → 进"可疑"桶，不计入统计
3. 角色权重：馆员/专家 5，普通用户 1，匿名 0.1；结合会话行为（点踩后立即复制/追问 = 强信号）
4. 双条件阈值：降权需「时间窗内 ≥N 个不同用户」，单次反馈绝不自动改权重
5. 不可逆操作人工卡点：下架/删文档必须人工确认；自动化上限是「降权 + 建工单」
```
外加**监控反馈本身**：点踩率分布与突增检测（某时段尖峰 = 可能在刷，或真出故障，两者都要告警但处置不同），保留审计日志与回滚能力。
若用 LLM 判断"反馈是否合理"，**必须先与人工标注对齐**（测一致率），未校准的 judge 不能做自动决策——这是第 2 次拷问的坑。

**生产经验总结**：
1. **知识治理的技术核心是"元数据 + 检索层过滤 + 可追溯"，组织核心是"owner + 签核"**，缺一半都不成立。
2. **时间感知的难点不是过滤，是"用问题里的日期检索"**——只用 `NOW()` 的系统在跨假期提问上必错。
3. **反馈闭环的自动化上限是"建工单 + 降权"，删改必须有人签字。**
4. **缓存 key 不带日期/知识版本，会让所有知识治理努力在最后一公里失效。**

4. **诚实收敛**：第 4 题承认"多加几台"、第 7 题承认只测一种故障，没有硬吹——这个习惯比多答对两道题重要得多。

### 核心不足（按优先级排序）

1. **缺"资源视角"这条主线（贯穿 Q1/Q4，最致命）**：看到 P99 暴涨就去猜组件慢，却不会先用 Little's law 判断"是算还是等"；容量规划只给"几台机器"的直觉，不会从"单请求资源 × QPS"推。这条主线不通，Q1、Q3 的慢请求定位、Q4 的瓶颈预判、Q7 的降级反噬（QPS 放大）会同时丢分——**这四题其实是同一道题**。
2. **量化能力普遍不足**：成本公式没展开到变量级、容量没有估算方法、灰度"观察一周"是拍脑袋、优化效果"看 QPS 和延迟"没有置信区间。高级工程师与中级的分水岭就在这里——**能不能把"大概""差不多"换成数字和区间**。
3. **生产中间件层仍停留在名词层**：熔断、限流、批处理、连接池、Outbox、对账 job，你都"知道"，但几乎每一处都缺落地细节（怎么触发、阈值多少、怎么回滚、怎么观测）。第 7 题 55 分是这一短板最直接的体现。
4. **质量可观测与评测体系薄弱**：judge 未校准（老问题第三次复发）、没有分层的 golden set、只依赖单一代理指标、把离线指标（召回率）搬到线上。这导致你对"静默降质"这类问题的所有答案都缺牙齿。
5. **自动化闭环缺边界感**：点踩多就自动降权/下架、指标差就自动回滚、缓存只按相似度失效——三处都缺"人工卡点 + 双条件阈值 + 审计回滚"。**敢自动化的前提是敢回滚，而你的设计里回滚路径都不清晰。**
