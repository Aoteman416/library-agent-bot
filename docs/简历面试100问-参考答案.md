## 一、项目概览与架构（1-10）

**1. 整体架构与数据流？**
一句话：FastAPI 单体的 RAG + Agent 客服系统。数据流为「用户输入 → 安全检查 → 意图分类（关键词加权，低置信时 LLM Function Calling 改写）→ 三通道路由（business / faq / rag）→ 检索或工具调用 → 生成 → SSE 流式返回」。
落点：`app/main.py` 注册 6 个路由（chat/auth/book/user/seat/admin）；`app/services/chat_service.py` 的 `ChatServiceV2.process` 是编排核心；`app/rag/` 提供检索。启动 `lifespan` 里做 `init_db()` + `rag_service.build_index()`。

**2. 为什么用 RAG 而不是微调/纯 LLM？**
三点：①图书馆规则会随学期、假期变动，**知识更新频率高，微调成本不可接受**，RAG 只需换文档重建索引；②**可溯源**是刚需——回答要能标出处，RAG 天然带 chunk 元数据；③**抑制幻觉**——把回答约束在检索内容内，而纯 LLM 会编造馆藏数据和规章制度。
另外本项目还能在无 LLM Key 时用离线模板模式跑通，RAG 保证"至少答得有依据"。

**3. 一次请求的端到端链路？**
`POST /api/v1/chat/stream` → `get_current_user` 解析身份 → `session_manager.get_or_create` → `chat_service.process` 产出事件字典 → `sse_event` 包装 → `StreamingResponse(media_type="text/event-stream")`。
事件序列：`session` → `route`（通道）→ `token`（逐块）→ 可选 `confirm`/`login_required`/`slot_required` → `sources` → `done`。前端 `fetch` + `resp.body.getReader()` 按行解析 `event:`/`data:`。

**4. "压降人工咨询量"怎么量化？**
诚实讲：本项目**没有真实线上流量**，无法给出真实压降比。可量化的是**可答率**：`admin_service.get_overview()` 返回 `total_questions / unique_questions / unresolved_count / resolved_count / channel_percentage`，用「RAG+FAQ 通道占比」和「低置信度转人工比例」作为代理指标。
正确表述：目标是把高频咨询（开放时间、借阅规则、续借、预约、查书）自动化，衡量口径是通道分布与未解决率，真实压降需上线后对比人工工单量。

**5. "可溯源"怎么实现？**
每个 chunk 带元数据 `{source, category, doc_type}`（`knowledge_service.load_file`），检索结果 `rag_service.get_sources()` 返回 `[{title, category, score}]`，API 用 `sources` 事件单独下发，前端渲染引用卡片。Prompt 也强制要求"回答末尾标注 `[来源：文档名]`"（`SYSTEM_PROMPT` 第 3 条规则）。

**6. 1 分钟向馆长介绍？**
"这是一个能 7×24 回答图书馆问题的机器人：学生问'几点闭馆''怎么续借''三体还有吗'，它直接答并告诉你是从哪一条规定来的；答不上来的会自动记下来交给馆员补充，或转人工。规则改了，您把文档换掉它就跟着变，不用改程序。"

**7. 最复杂的模块？**
对话编排 `chat_service.py`。因为它是**状态机 + 多通道 + 多轮**的交汇点：要处理 `idle/collecting_slots/confirming/completed` 四阶段、7 类意图、3 个通道、登录升级、二次确认超时、指代消解，还要保证每一步都能流式产出事件。比纯检索复杂得多。

**8. 最大技术卡点？**
口语化查询无法路由——"有三体吗"没有任何意图关键词，加权分类器直接判 `unknown`。解法是加了一层 `intent_rewriter`：配了 Key 就用 **LLM Function Calling** 调 `route_intent` 工具输出结构化意图+书名+槽位；没 Key 就用**启发式**（书名号优先，否则剥停用词和查询动词取核心词）。两条路都保留，保证降级可用。

**9. 接入微信/小程序要改什么？**
①会话标识：用微信 openid 当 `user_id`，`session_id` 仍由服务端生成并下发；②SSE 要换成**微信的被动回复/客服消息推送**（微信不支持 SSE，得改成异步回调 + 消息排队）；③`X-Public-Device` 头逻辑可复用；④权限矩阵里 `anonymous_allowed` 需按微信授权态调整；⑤若要语音，加 ASR 前置。

**10. 怎么证明"显著提升"？**
用 `eval/run_eval.py` 的**回归数据**证明检索质量提升（如 ngram vs BGE 的 Recall/MRR 对比），用 `admin_service` 的通道分布证明自动化率。诚实说法：目前是**离线可量化**（48 条标注集 + 指标报告），**线上效果需部署后验证**——这正是我想在真实场景里做的事。

## 二、RAG 检索管道（11-28）

**11. 检索管道设计？**
两阶段：①**索引**：`knowledge_service` 加载 md/txt → 按 `#`/`##` 分节 → 推断 `doc_type` → 自适应分块 → `embedder.embed_batch` → `store.add_batch`；②**在线**：`embed_query` → `store.search(top_k=10)` → 精排 → 取 `rerank_top_n=3`。
`Retriever` 通过 `create_embedder` / `create_store` 工厂注入，**稀疏/稠密、内存/Chroma 自由组合**，上层无感知。

**12. 自适应分块怎么做？**
按 `doc_type` 选参数（配置在 `settings.CHUNK_STRATEGY`）：
- `policy_doc` 政策文件：500/100（大块保留上下文）
- `faq_doc` FAQ：300/0（按问答对，无需重叠）
- `guide_doc` 指南：800/150（按章节，中等重叠）
- 未分类：200/50（全局默认）
`doc_type` 由 `knowledge_service._infer_doc_type` 按**文件名 + 章节标题关键字**推断（如含"规则/政策/制度"→policy）。

**13. chunk_size/overlap 为什么重要？**
size 太小切断语义、检索到的块答不完整；太大引入噪声、稀释向量表征、占 token。overlap 保证跨块边界的信息不丢（比如一条规则的前半句在块 A、后半句在块 B）。本项目按文档类型给不同值，并对 `overlap >= size` 做了 clamp 保护。

**14. overlap 的副作用与权衡？**
副作用：①**重复内容占索引**，Top-K 可能同时召回两段高度重叠的块，浪费窗口；②**向量相似度被重复项抬高**，挤压其他候选；③存储与计算成本上升。
权衡：FAQ 是独立问答对，语义自足，直接设 0；政策/指南跨块依赖强，给 100/150。这是"按类型差异化"而非一刀切。

**15. 为什么选 BGE 而非 OpenAI/m3e？**
①**中文语义强**：BGE-large-zh 在中文检索榜单长期靠前；②**可私有化部署**，图书馆数据不出内网，合规友好；③**成本**：开源模型自建无按量费用，OpenAI embedding 有持续调用成本和数据出境问题；④支持 `normalize_embeddings`，余弦相似度即点积，检索快。

**16. 为什么要加查询指令前缀？**
BGE 官方建议：短查询（问句）与长文档（陈述句）在语义空间分布不同，给 query 加"为这个句子生成表示以用于检索相关文章："能让两者**对齐到同一语义空间**。
落点：`EMBEDDING_QUERY_PREFIX`，仅 `embed_query` 加、文档侧不加（代码里 `embed()` 不加前缀，`embed_query()` 才加）。不加前缀会让"问句式 query 匹配陈述式文档"的召回率明显下降。

**17. 维度多少？存什么？**
稠密：`BAAI/bge-large-zh-v1.5` = **1024 维**（`get_sentence_embedding_dimension()` 动态读取；小模型 bge-small 为 512 维）。
存的是 `{chunk_id: [1024 floats], document: 原文, metadata: {source, category, doc_type}}`。稀疏模式存的是 `{term: tf-idf 权重}` 字典。**存向量也存原文**，因为生成阶段要用原文拼上下文。

**18. Chroma 承担什么？怎么持久化？**
`ChromaStore` 用 `PersistentClient(path=CHROMA_PERSIST_DIR)` 落盘，`get_or_create_collection(metadata={"hnsw:space": "cosine"})`，**进程重启直接复用索引**（`build_index` 里 `store.size == len(chunks)` 就跳过重建）。
它负责 ANN 检索 + 原生 `where` 元数据过滤。注意：Chroma 的 metadata 只支持 str/int/float/bool，代码统一 `str(v)` 转换。

**19-20. 混合检索怎么做的？融合方式？** `[诚实]`
**必须收敛表述**：我实现的是「**向量召回为主 + 精排阶段融合字面特征**」，不是经典双路召回混合。
具体：只有一条向量召回路径（`store.search`），在精排时算 `score = 0.75 × 语义cosine + 0.25 × 词项覆盖率`，词项覆盖 = `|query词项 ∩ 文档词项| / |query词项|`。
之所以仍有效：字面分兜住了"3楼""0.1元"这类**专有名词精确匹配**。
**真做混合**需要：另建 BM25 索引做关键词召回 → 与向量召回各取 Top-K → 用 **RRF**（`score = Σ 1/(60+rank)`）或加权融合。代价是多维护一套索引、双写和分词一致性。这是我列出的下一步。

**21. 为什么需要 Cross-Encoder？Bi vs Cross 区别？**
**Bi-Encoder**：query 和 doc 各自独立编码成向量，比对余弦。快（doc 向量可离线预计算），但 query 与 doc **无交互**，精度有限。
**Cross-Encoder**：把 `(query, doc)` **拼在一起**过一遍模型，直接输出相关性分数。有充分交互，精度显著更高，但**必须在线计算**，无法预存，所以只能用于重排 Top-K 少量候选。
本项目：初检用向量（快、全），精排用 Cross-Encoder（准、少）——典型的**粗排+精排**两阶段。

**22. 重排在哪介入？Top-K 和 Top-N？**
`Retriever.retrieve`：先 `store.search(top_k=10)`（配置 `TOP_K=10`），再 `reranker.rerank` 后截断到 `rerank_top_n=3`（配置 `RERANK_TOP_N=3`）。
判断分支：`if self.reranker.name == "noop"` 走融合打分，否则走 `CrossEncoderReranker`（`bge-reranker-large`，`model.predict(pairs)`）。

**23. 重排增加多少延迟？怎么权衡？**
Cross-Encoder 要对 K 个 `(query, doc)` 对逐个推理，CPU 上 K=10 通常几百毫秒量级，是管道里**除 LLM 外最重的一段**。
权衡手段：①只对初检 Top-10 重排，不重排全库；②`batch_size=32` 批量推理；③可开关（`RERANKER_ENABLED`），默认的融合打分零成本；④依赖缺失自动降级 Noop，服务不中断。诚实讲：**我没做严格延迟基准测试**，这是待补的量化项。

**24. 低置信度怎么定义？**
代码里是**规则阈值**：`RAG_LOW_CONFIDENCE_THRESHOLD = 0.15`，即 `docs 为空 或 docs[0].score < 0.15` 判为低置信。
诚实说明：这个 0.15 是**经验值**，不是用标注集调出来的最优阈值——因为不同 Embedding（稀疏 TF-IDF 分数偏低 vs 稠密余弦分数偏高）的分数分布差异很大，**共用阈值不严谨**。正确做法是分模式标定阈值，或用标注集画 PR 曲线选点。

**25. 转人工 vs 带免责声明？**
当前实现：**未检索到文档** → 返回兜底话术 + 三条建议（换关键词 / 转人工 / 官网），同时 `admin_service.record_unresolved` 记录待回流；**有文档但分数低** → 仍然生成，但打 `low_confidence` 标记，且**不写入 FAQ 缓存**（避免污染缓存）。
决策依据：完全没依据就别硬答（幻觉风险高），有部分依据就答但标注来源让用户自行判断。

**26. Prompt 怎么约束引用来源？**
`SYSTEM_PROMPT` 里写死规则：①"优先使用参考文档中的信息，不要编造馆藏数据或规章制度"；②"如果参考文档中没有相关信息，请回复：抱歉，我暂时无法回答…"；③"回答末尾标注信息来源，格式为 [来源：文档名]"。
上下文用 `build_context` 拼成 `[文档1] 内容\n来源：xxx` 格式，**每个块都带来源**，让模型有据可依。另外"禁止行为"里明确"不编造不存在的规定或数据"。

**27. 幻觉率怎么衡量？**
诚实讲：**没有做端到端幻觉率标注**。用的是两个代理指标：
- `eval/run_eval.py` 的 **KeywordHit@K**：Top-K 拼接文本是否覆盖标注的**必含关键词**（衡量"这段料够不够直接回答"）；
- 线上：**低置信度转人工比例** + 用户反馈评分（`feedback_stats` 的 `avg_rating` / `low_rating_count`）。
真要测幻觉，需要人工标"哪些句子无检索依据"，或上 LLM-as-judge（且必须先用人工样本校准 judge）。

**28. 元数据过滤作用？举例。**
`store.search(metadata_filter=...)` 支持按 `{source, category, doc_type}` 精确过滤，Chroma 走原生 `where`（多条件隐式 AND），内存库走 `_match_meta`（全等匹配）。
举例：只搜政策类 `{"doc_type": "policy_doc"}`；或限定某份文档 `{"source": "借阅规则.md"}`；评测时 `relevant_chunk_ids` 就是用 `source + category` 双命中来判定"相关"。

## 三、Agent 与多轮对话（29-43）

**29. 工具怎么组织？列几个。**
以 **Python 方法 + 服务层**封装，而非 LangChain 式的 Tool 对象：
- `book_service.search` → 馆藏检索
- `user_service.get_borrow_info` / `renew` → 借阅查询 / 续借
- `seat_service.reserve` → 座位预约
- `rag_service.retrieve` → 知识库检索
- 另有 `human_transfer`（转人工）
路由不靠通用 Tool 循环，而是**意图 → 通道 → 具体服务方法**的显式分发（见 `_route_business`）。

**30. Function Calling 怎么用？**
不是用来循环调用业务 API，而是用在**意图路由层**：`intent_rewriter._INTENT_ROUTE_TOOL` 定义了一个 `route_intent` 函数（参数 `intent` 枚举、`query`、`book_title`、`date`、`start_time`、`end_time`、`area`），让 LLM 输出**结构化意图 + 槽位 + 改写查询**。
用 Function Calling 而非自由 JSON 的理由：**模型原生保障 schema 合法性**，比"请输出 JSON"稳定得多。调用入口 `llm_client.chat_with_tools()`。
触发条件是 `score <= 2.0`（关键词分类低置信），高置信不打扰 LLM，省 token。

**31. 多工具/多意图怎么调度？**
两层机制：
①**分类层冲突消解**：`IntentClassifier` 取 top1 和 top2，若 `top2 >= top1 × 0.8` 且 top1 是业务意图、top2 是 FAQ 意图，则**优先返回 FAQ**（保守优先，避免误触发写操作）；
②**执行层**：当前是**单意图串行**——一次只推进一个业务流程（槽位填充→确认）。真正的多意图并行调度（DAG/Plan-and-Execute）**没有实现**，属于下一步。

**32. 二次确认怎么实现？状态存哪？**
`DialogueState.set_pending_confirm(action, payload, ttl=300)`：生成 `confirm_id`，把 `{action, payload, confirm_id, expires_at}` 存进**会话状态对象**，phase 转为 `confirming`。
用户回"确认"→ `state.confirm()` 取出 payload 执行；回"取消"→ `clear_pending_confirm()`；超过 5 分钟 → `is_confirm_expired()` 判超时作废；回复模糊 → 提示"请明确回复确认或取消"。
**状态存在 `Session.state`（进程内存），不是 Redis**。

**33. 会话管理引擎设计？存什么？**
`Session` 对象存：`session_id`、`user_id`、`is_public`、`created_at`、`last_activity`、`messages[]`、`state: DialogueState`。
`DialogueState` 存：`intent`、`phase`(idle/collecting_slots/confirming/completed)、`slots`(槽位及填充状态)、`pending_confirm`、`pending_query`。
`SessionManager` 用 `Dict[session_id, Session]` 管理，带超时清理（`_cleanup_expired`）。

**34. 会话存在哪？** `[诚实]`
**进程内存**。`session_manager._sessions` 是一个普通 Python 字典，**Redis 在系统里只用于 FAQ 语义缓存和限流分布式计数**，没有存会话。
诚实说法："会话上下文我落地的是进程内内存版，Redis 用在热点缓存和限流上。多实例时会话需要外置到 Redis——这是我已设计、待上线的方案。"
多实例的两个具体故障：①第 2 句被 LB 转到另一实例 → `get_or_create` 找不到 session → **新建会话，上下文断裂**；②`confirming` 阶段在实例 A，用户回"确认"到实例 B → **无 `confirm_id`，确认永远失败**。
外置的坑：`DialogueState`、`Session` 含 `datetime` 对象，建议转 JSON（时间戳转 ISO 字符串）存储，并把超时逻辑映射为 Redis key 的 `EXPIRE`。

**35. 滑动窗口怎么实现？窗口多大？**
`Session.add()` 里：`self.messages = self.messages[-(MAX_HISTORY_TURNS * 2):]`，`MAX_HISTORY_TURNS = 10`，即**保留最近 10 轮（20 条消息）**。
滑出去的历史**直接丢弃**（不做摘要压缩）。另外 `format_chat_history(history, max_turns=6)` 在拼 Prompt 时**再收一轮到 6 轮**，因为给 LLM 的上下文比给系统的历史要更省 token。

**36. Token 预算动态裁剪？截断 vs 压缩？** `[诚实]`
诚实说法：我实现的是**固定条数截断**（滑动窗口 10 轮 / Prompt 内 6 轮），**不是按真实 token 数动态裁剪**——没有接 tokenizer 去累加 token 并二分裁剪。
两者区别：截断是**按消息条数**粗暴丢弃 oldest，可能一次丢掉一大段也可能留太多；压缩是**把早期历史摘要成一段**（或用小模型总结），保留语义但省 token。
正确做法：用 `tiktoken` 累加真实 token，超预算时**优先保留 system + 检索上下文 + 最近 N 轮**，把更早的轮次做摘要。这是我的改进项。

**37. 超预算优先丢什么？**
优先级从**先丢到最后丢**：①更早的对话轮次（离当前意图最远）→ ②重复/寒暄内容 → ③检索文档里分数低的块（减少 `TOP_K`）→ **绝不能丢**：系统 Prompt 约束、当前问题、分数最高的 Top 文档、当前槽位与待确认状态。
理由：丢历史只是损失连贯，丢约束和依据会直接引发幻觉和越界。

**38. 多意图如何澄清追问？举例。**
用 `DialogueState` 的**槽位追问**：`start_collection(intent, template)` 初始化槽位 → `next_question()` 按 `missing_slots()` 顺序生成追问 → 用户回答进 `_fill_slots` 填充 → 全部填满才进确认。
例：用户说"帮我预约座位" → 缺 `area/date/start_time/end_time` → 逐条追问"请告诉我想预约的区域（如「3楼自习室」）"；若用户一次说"明天下午3楼自习室2点到4点"，`extract_entities` 会**一次填满多个槽位**（混合填充），直接进确认。
真正的"多意图消歧"（如"帮我查书并预约"拆成两个意图让用户选）**未实现**。

**39. 越界/敏感怎么拒答？**
三道防线：①`security_guard.check_injection` 正则黑名单（指令覆盖、数据泄露、角色切换、jailbreak 等），命中直接拦截并返回提示；②`SYSTEM_PROMPT` 的"禁止行为"章节（不回答与图书馆无关问题、不编造、不索要隐私）；③`CHAT_SYSTEM_PROMPT` 里闲聊通道也明确"不回答政治、色情、暴力的无关内容，遇到请礼貌说明只能回答图书馆相关问题"。
匿名权限矩阵也会拒：`permissions.py` 里匿名只能访问 `book_search/seat_availability/faq_qa/human_transfer/kb_query`，其他引导登录。

**40. 意图识别怎么做的？**
**加权关键词分类器**（`IntentClassifier`），不是模型：7 个意图各配 `[(关键词, 权重)]`，累加命中权重取最高；7 类为 `human_transfer / book_search / borrow_manage / seat_reserve / policy_faq / resource_guide / navigation`，映射到 3 个通道（business / faq / rag）。
**低置信（score ≤ 2.0）才调 LLM Function Calling** 兜底。这样高频明确问题零 LLM 成本，只有口语化/模糊的才付费。

**41. 工具结果出错/超时怎么办？**
工具调用**同步返回**结果 dict（如 `seat_service.reserve` 返回 `{ok, message, reservation}`），失败时把 `message` 直接转成用户可见文本（"❌ 预约失败：…"），**不做自动重试**。
LLM 侧：`llm_client.chat/chat_stream` 异常 → 返回 None / 抛异常 → 上层降级离线模板。**没有重试，也没有熔断**（见第 53 题）。

**42. 中断后能恢复吗？**
能，靠**会话超时 + 状态持久化**：会话 30 分钟无活动失效（公共一体机 10 分钟），期间回来 `get_or_create` 能取回同一个 session，`DialogueState` 里的 phase/slots/pending_confirm 都还在。
另外消息会 `persist_message` 落 `messages` 表（DB 可用时）。**但进程重启会丢内存会话**——这是会话外置 Redis 的又一个动机。二次确认本身 5 分钟过期，超时会提示重新发起。

**43. 工具结果怎么回填？格式校验？**
业务通道**不经过 LLM 二次生成**：`_execute_confirm` 拿到 `result` 后**直接格式化成文本**流式吐出（如"✅ 预约成功！…预约编号：xxx"）。
优点：零幻觉、快、省 token。缺点：话术固定不自然。
校验：`llm_client.chat_with_tools` 里 `json.loads(arguments)` 解析 + 意图值必须落在 `_INTENT_LABELS` 枚举内，否则归 `unknown`；`_clean_slot` 做空值/空白清洗。业务服务层自己做参数校验。

## 四、高可用工程化（44-61）

**44. 为什么选 FastAPI？**
①**原生 async**：LLM 调用、流式输出都是 IO 密集，async 能撑高并发；②**Pydantic 自动校验**请求体 + 自动生成 OpenAPI 文档，调试快；③**依赖注入**（`Depends(get_current_user)`）写鉴权很干净；④性能接近 Node/Go 级别的 Python 框架。Flask 同步模型不适合流式，Django 太重。

**45. SSE vs WebSocket？为什么 SSE？**
SSE：**单向**（服务器→客户端）、基于 HTTP、**自动重连**、简单、可被 Nginx 正常代理；WebSocket：**双向**、需升级协议、更复杂。
对话场景只需要**服务器单向推送 token**，SSE 足够且更轻、更稳。客户端发消息仍用普通 POST。
响应头设了 `Cache-Control: no-cache`、`X-Accel-Buffering: no`（关键！否则 Nginx 会缓冲导致不实时）、`Connection: keep-alive`。

**46. SSE 怎么从 LLM 流到前端？**
`llm_client.chat_stream` 用 `httpx` 的 `client.stream("POST", ..., stream=True)` 逐行读 `data: {...}`，解析 `choices[0].delta.content` yield 出来 → `rag_service.stream_answer` 包成 `{"event":"token"}` → `chat.py` 的 `sse_event()` 格式化成 `event: token\ndata: {...}\n\n` → `StreamingResponse` 吐出 → 前端 `reader.read()` 按行解析 `event:`/`data:` 并 `bubble.textContent += content`。
降级模板模式下也用 `chunk_text(answer, size=12)` 切成小片**模拟流式**，保证前端体验一致。

**47. JWT vs Session-Cookie？**
JWT **无状态**：token 自带 `sub/role/exp`，服务端不存会话，适合分布式和水平扩展；Session-Cookie 要在服务端存 session（或集中到 Redis），有状态。
JWT 缺点：**难以主动失效**（吊销要等过期或维护黑名单）。本项目用**短期 access（60 分钟）+ 长期 refresh（7 天）**组合缓解。
代码里 `create_access_token` / `create_refresh_token`，`get_current_user` 校验 `type == "access"`。

**48. JWT secret 怎么管？token 过期刷新？**
secret 从环境变量读：`JWT_SECRET_KEY`（默认 `change-me-in-production`，**生产必须改**，docker-compose 里也用 `${JWT_SECRET_KEY:-...}` 注入）。
过期：payload 带 `iat/exp`，`decode_token` 校验 `exp`，过期抛 `UnauthorizedError`。刷新：登录接口同时返回 access 和 refresh，客户端用 refresh 换新 access（**当前只实现了签发，没有实现 refresh 换发的接口**——诚实说明）。
降级：优先用 `python-jose`，缺依赖时 `_hmac_encode` 用内置 hmac-sha256 自签，保证不崩。

**49. 限流算法？**
**滑动窗口**（`RateLimitMiddleware`）。Redis 可用时：`incr` + 首次 `expire(window)`（固定窗口的简化实现，靠 TTL 滚动）；Redis 不可用时：进程内 `deque`，`while dq[0] <= now - window: popleft()` 剔除过期再计数，**是真滑动窗口**。
精准滑动窗口（Redis ZSET + `ZREMRANGEBYSCORE`）是可选升级。

**50. 阈值怎么定？超限返回什么？**
默认 **用户维度 30 次/60秒、IP 维度 100 次/60秒**（`RATE_LIMIT_PER_USER / PER_IP / WINDOW_SECONDS`），按"真人对话频率远低于此，但足以挡住脚本刷"来定。
超限：HTTP **429** + 统一错误码 **3001**（"请求过于频繁，请稍后重试"）+ 响应头 `Retry-After: <window>`。
白名单：`/health`、`/docs`、`/openapi.json`、`/redoc` 跳过。用户维度取 `Bearer sub` 或 `X-Demo-User`，匿名退化为 IP 维度。

**51. Redis 缓存热点问答，命中率多少？怎么失效？** `[诚实]`
**命中率我没在线上统计过**（无真实流量）。代码里有 `stats()` 返回 `hit_count/miss_count/hit_rate/size`，接口可查，但需要真实流量才有意义。
缓存设计：key = 问题文本小写去空格（Redis 后端用 `md5` 做 key，前缀 `faq_cache:`），value = `(answer, sources, vector, created_at)`；**精确匹配优先，未命中再做语义匹配**（n-gram TF-IDF 余弦 ≥ **0.85**）；容量 **LRU 500 条**，**TTL 3600 秒**过期。
失效三路径：TTL 自然过期（`_touch` 时检查）、LRU 淘汰、`invalidate(question)` 手动删。**知识库更新后没有主动清缓存**——这是隐患，正确做法是 reindex 时 `faq_cache.clear()`。

**52. 降级策略怎么设计？**
全局"**依赖缺失/异常 → 自动降级，服务不中断**"：
- LLM 不可用（无 Key / 调用失败 / 流式异常）→ 离线模板 `_template_answer`（用检索到的知识块直接组装，仍带来源）
- 稠密 Embedding 初始化失败 → 回退稀疏 ngram
- Chroma 不可用 → 回退内存向量库
- Redis 不可用 → 回退进程内缓存/计数
- DB 不可用 → 回退内存 SQLite 演示 / Mock 数据
- python-jose 缺失 → 回退内置 hmac 签名
- Cross-Encoder 缺失 → 回退融合打分
关键：**每一层降级都记 warning 日志**，不是静默吞掉。

**53. 熔断与重试机制？** `[诚实]`
**必须收敛**：我实现的是**降级（Degrade）**，**没有熔断（Circuit Breaker），也没有重试**。
- **降级**：有——LLM 失败走离线模板（见上题）。
- **熔断**：无。`llm_client` 失败只 `return None` 或抛异常，上游不会"记住失败并快速失败"。
- **重试**：无。
缺熔断的危害：上游偶发超时（比如 30s）时，每个请求都会真实打到 LLM 并**傻等满超时**才降级，高并发下连接池被占满，可能雪崩，且浪费配额。
正确补法（30 行内可实现）：连续失败 N 次（如 5）→ 打开熔断 30 秒，期间直接降级不调 LLM；用 `tenacity` 对**超时/5xx**做指数退避重试 2 次，**4xx 不重试**。

**54. 哪些错误重试，哪些不重试？**（设计口径）
- **重试**：网络超时、连接重置、5xx、429（带 `Retry-After`）——这些是**瞬时/服务端**问题，重试有概率成功。
- **不重试**：400/401/403（请求本身错，重试必然再错）、业务校验失败（如"该书不可续借"）、写操作的非幂等失败（除非有幂等键）。
- 注意：重试必须**幂等**，本项目 `confirm_id` 就是二次确认的幂等凭证。

**55. LLM 持续不可用，系统怎样？**
**部分可用（降级可用）**，不会整体崩溃：FAQ 通道走 `_faq_fast_match` 关键词精确匹配、RAG 通道走离线模板（直接用检索块组装答案并标来源）、业务通道（查书/借阅/预约）**完全不依赖 LLM**照常工作。
真正受影响的只有：需要自然语言的生成式表达、口语化意图改写（回退启发式）、unknown 闲聊（回退固定话术）。
所以 LLM 挂掉后，系统退化成"检索式问答"，核心咨询能力仍在。

**56. Docker Compose 包含哪些服务？**
三个：
- **app**：`build: .`（Dockerfile），端口 `8000:8000`，`depends_on: [mysql, redis]`，挂载 `./data:/app/data`
- **mysql:8.0**：库 `library_service`，utf8mb4，端口 3306，卷 `mysql_data`
- **redis:7-alpine**：端口 6379
app 的环境变量显式打开生产开关：`DEBUG=false`、`DB_ENABLED=true`、`REDIS_ENABLED=true`、`RATE_LIMIT_ENABLED=true`、`JWT_SECRET_KEY`，RAG 三项（`EMBEDDING_MODE/VECTOR_STORE_MODE/RERANKER_ENABLED`）用 `${VAR:-default}` 从宿主注入。

**57. 容器化好处？配置怎么区分？**
好处：①**环境一致**（开发与生产同一镜像，避免"我机器上能跑"）；②一键拉起 MySQL+Redis 依赖；③数据卷持久化（`mysql_data`、`./data`）。
配置区分：全部走**环境变量**（`config.py` 用 `os.getenv` 读，支持 `.env`）。compose 里写死生产值/从宿主注入，本地 `.env` 写开发值。代码零改动，只换配置——符合 12-Factor。

**58. 结构化日志记了哪些字段？** `[诚实]`
诚实说：日志是**统一格式化的单行文本**，不是 JSON 结构化：
`%(asctime)s | %(levelname)-7s | %(name)s | %(message)s`
即「时间 | 级别 | logger 名 | 消息」。
记的内容：意图路由结果（`intent/query/title/slots`）、索引构建（embedding/store/分块数）、降级事件（LLM 失败、Redis 不可用、Chroma 回退）、限流后端选择、注入拦截（`pattern` + 原文前 100 字符）、流式中断。
**真正的结构化（JSON + trace_id + request_id）没做**，这是可观测性的一块缺口（见 59 题）。

**59. 链路追踪用的什么？** `[诚实]`
**没有接入分布式链路追踪组件**（没有 Jaeger / Zipkin / OpenTelemetry，也没有 trace_id 透传）。
诚实说法："我做了统一格式的日志和运维看板数据接口，**链路追踪这块我只是设计了 span 划分方案，实际没有集成 OpenTelemetry**，简历上这句写得过了。"
设计口径（如果被追问方案）：一次请求一个 trace，span 划分为 `gateway → ratelimit → classify → retrieve(vectors) → rerank → llm.stream → persist`，tag 记 `session_id/intent/channel/top_k/mode/llm_model`。落地时用 OpenTelemetry 自动埋点 + 手动 span，导出到 Jaeger。

**60. 运维看板用什么？监控什么？** `[诚实]`
**没有接 Grafana/Prometheus**，是**自研的数据接口 + 前端页面**：`admin_service.get_overview()` 提供 JSON，前端渲染。
监控指标：总提问数/去重提问数、未解决数/已解决数、反馈数与平均分、待回流知识数、热门问题 Top5、通道分布与占比（`business/faq_fast/rag`）；`/health` 返回 db/llm/embedding/vector_store/reranker 的开关状态；`/api/v1/chat/feedback/stats` 返回 `avg_rating / helpful_rate / low_rating_count`。
**没有时序存储和告警**（无法看趋势曲线和阈值告警），这是缺口。

**61. 高并发瓶颈在哪？**
第一瓶颈是 **LLM 供应商**（单次生成数百 ms～数秒，且受 RPM 配额限制）；其次是 **Cross-Encoder 重排**（CPU 密集，K=10 逐对推理）；再次是**稠密 Embedding 编码**（若开 BGE）；内存向量库在**万级以内**线性扫描还扛得住，再大要换 HNSW（Chroma）。
MySQL 不是瓶颈（查询都很轻量，且有索引）。
应对：FAQ 语义缓存挡掉大量重复问题、降级链路保证 LLM 挂了也能答、限流保护自身、把重排/Embedding 设为可关闭。

## 五、质量评估与持续迭代（62-71）

**62. 评测集怎么构建？样本量？**
人工标注：`data/eval/qa_eval.jsonl`，**48 条**样本。每条字段：`id / query / relevant_source / relevant_category / must_contain`。
"相关"的判定是 **分块的 source 与 category 元数据同时命中标注值**，所以粒度是**知识条目**而非整篇文档。
诚实说明：48 条偏少，覆盖的是高频问题；要支撑严格结论需要扩到数百条并分层（按意图/难度/长度）采样。

**63. 召回质量指标？**
`eval/run_eval.py` 计算 5 个指标，在 **K=1/3/5** 三档：
- **Recall@K** = |Top-K ∩ 相关| / |相关总数|（召全能力）
- **Precision@K** = |Top-K ∩ 相关| / K（排得准不准）
- **MRR** = 1 / 首个相关结果排名（首条命中能力）
- **HitRate@K** = Top-K 是否出现相关（可用率）
- **KeywordHit@K** = Top-K 拼接文本是否覆盖全部必含关键词（**能否直接回答**——我最看重这个，因为它最接近"用户能不能被满足"）
实现细节：每个样本只检索一次（取最大 K），其余 K 截断前缀，保证 K=1/3/5 指标**来自同一次排序**，可比性强。

**64. 精准程度怎么评估？LLM-as-judge？**
用 **Precision@K + MRR + KeywordHit@K** 三个检索侧指标衡量，**没有用 LLM-as-judge**（无 judge 实现）。
如果要上 judge：必须先用人工标注样本**校准**（测 judge 的准确率/召回、调 prompt 和阈值），**避免用与生成同一个模型当 judge**（self-bias 会系统性放水），并让 judge 输出"哪句话无检索依据"以便人工复核。

**65. 幻觉率怎么定义和计算？**
当前**没有端到端幻觉率指标**。代理口径：
- `KeywordHit@K` 作为"依据充分性"的代理；
- 线上用**低置信度转人工比例** + **低分反馈占比**（`low_rating_count`）作间接信号。
若定义幻觉率：应为「回答中**无检索依据支撑**的陈述句数 / 总陈述句数」，需人工或 judge 逐句标注。这是待补的能力。

**66. 回归测试怎么跑？改 prompt 会回归吗？**
`python eval/run_eval.py` 可复现跑全套指标并输出 `report.md/report.json`。支持 `--compare` 对比稀疏 vs 稠密、`--no-rerank` 只测召回、`--top-k` 指定 K、`--chunk-size/--chunk-overlap` 调分块做参数实验。
**改 prompt 目前不会自动触发回归**——评测只覆盖检索侧，不覆盖生成侧（因为生成需要真实 LLM + 生成质量标注）。正确做法是把评测接入 CI，并对生成侧建"golden answer"集。这是改进项。

**67. 未识别问题聚类模块？** `[诚实]`
诚实说法：**没有聚类算法**。实现的是 `admin_service` 里的**频次统计**：`_question_counts: Counter`，`record_question(question)` 累加，`get_hot_questions(top_n)` 返回 `Counter.most_common(top_n)`。
**聚类 vs 频次统计的差距**：频次统计按**完全一致的字符串**计数，"续借怎么弄"/"如何续借"/"借阅延期"会被当成 3 个独立问题，馆员要重复看重复补。语义聚类（embedding + KMeans/层次聚类）能把同义不同表述归成一簇，**一次标注覆盖一类**。
这是我明确列出的下一步，简历里"聚类模块"的说法应改为"未识别问题记录与热度统计"。

**68. 低置信度回流的人工标注流程？**
流程：①`_route_rag` 判低置信 → `record_unresolved(question, session_id, confidence)` 入 `_unresolved`（status=pending）；②馆员在后台看 `get_unresolved(status="pending")`；③调用 `resolve_unresolved(index, answer)` 补标准答案 → 该条标记 `resolved` 并写入 `curated_answer`，同时**加入 `_pending_knowledge` 队列（status=pending_review）**；④审核通过后才真正进知识库并 `reindex`。

**69. 回流有审核门吗？错误回流会怎样？**
**有审核门**：`_pending_knowledge` 的初始状态是 `pending_review`，不是直接生效；馆员补的答案也要经过这一步。
但**存在风险点**：用户低分反馈（rating ≤ 3）会**自动** `append` 进 `_pending_knowledge`（`source="low_rating_feedback"`），只记 `rating/comment`，**没有内容验证**。若审核不严或误触/恶意反馈，错误知识可能污染知识库 → 后续检索召回错误块 → 更多人拿到错答案 → 差评更多，形成**垃圾进垃圾出的自激循环**。
改进：①反馈入队时带原始问答对供审核；②设"同一问题 N 次反馈才入队"的阈值；③知识库**版本化 + 一键回滚**；④新条目灰度生效并监控指标。

**70. 闭环跑过几轮？效果提升多少？** `[诚实]`
诚实说：**闭环机制搭好了，但没有真实线上轮次数据**——没有真实用户流量，所以谈不上"运行了 N 轮、提升了 X%"。
可讲的量化结果只有**离线实验**：用 `run_eval.py --compare` 对比 ngram vs 稠密 BGE、`--chunk-size/--overlap` 对比不同分块参数、`--no-rerank` 对比加不加精排，看 Recall/MRR/KeywordHit 的变化来驱动参数选择。
正确表述："闭环的流程和数据结构已经实现，效果验证目前停留在离线评测层面。"

**71. 怎么防止评测集被刷分（过拟合）？**
①**评测集独立于知识库构建**：标注的是"期望命中的知识条目"，不是"让模型背答案"；②**保留独立测试集**，调参只用一部分，最终在未见过的问题上复测；③**定期扩充与轮换**样本，避免长期对着同一批题调；④**看多个指标**（Recall/Precision/MRR/KeywordHit），只优化单指标容易走偏；⑤线上指标（反馈分、转人工率）作为**最终裁判**，离线指标只是代理。

## 六、技术基础（72-81）

**72. GIL 对服务并发的影响？**
GIL 保证同一时刻只有一个线程执行 Python 字节码，**CPU 密集任务无法靠多线程并行**。对本服务：LLM 调用、DB 查询、Redis 都是 **IO 密集**，await 时会释放 GIL，所以 async 并发依然有效。
但 **Cross-Encoder 重排、稠密 Embedding 编码是 CPU 密集且同步的**，会**阻塞事件循环**——这是真实风险（见 73/74）。

**73. 用过 async/await 吗？哪些必须异步？**
用了。`process`、`stream_answer`、`chat_stream`、`chat`、`chat_stream(llm)` 全是 `async def` 并用 `AsyncIterator` yield 事件；LLM 调用用 `httpx.AsyncClient`。
**必须异步的场景**：SSE 流式（要边等边推）、并发 LLM 调用、高并发 IO。
**踩过的坑**：`_template_answer`、重排、Embedding 编码都是同步函数，直接在 async 里调用会阻塞——正确做法是用 `run_in_executor` 丢到线程池（**当前没做**，是性能改进项）。

**74. 怎么避免 CPU 密集阻塞事件循环？**
现状：没有处理（重排/Embedding 同步跑在事件循环里）。
标准解法：①`asyncio.to_thread()` / `loop.run_in_executor` 把 CPU 密集调用丢线程池；②用 `ProcessPoolExecutor` 跑重模型（绕开 GIL，真正并行）；③把重排/Embedding **拆成独立微服务**，用队列异步化；④部署时用 **多 worker（uvicorn --workers N）** 分摊。
这是本项目明确的性能改进点。

**75. Java vs Python 更熟哪个？优劣？**
（按个人实际情况答，参考口径）主力是 Python。对比：Python 开发效率高、AI 生态（transformers/httpx/fastapi）无可替代、适合快速迭代；Java 类型安全、JVM 性能与并发模型成熟、企业级生态（Spring）完善、适合大型团队协作和长周期维护。
后端选型上：AI/数据类服务选 Python，高吞吐交易系统选 Java。

**76. 用到过哪些数据结构？**
- **哈希（dict）**：稀疏向量 `{term: weight}`、`_sessions` 会话字典、`_index_by_id` 分块索引、意图权重累加
- **Counter/OrderedDict**：TF-IDF 词频、IDF、问题热度统计、LRU 缓存（`OrderedDict` + `move_to_end`）
- **deque**：限流滑动窗口（左端弹出过期时间戳）
- **堆/排序**：Top-K 结果 `sort(key=score, reverse=True)`
- **树/图**：ANN 的 **HNSW 图**由 Chroma 内部实现（见 77）

**77. 为什么需要 ANN？了解 HNSW 吗？**
精确 KNN 要算 query 与**全库每个向量**的相似度，O(N·d)，百万级就无法在线响应。ANN 用**牺牲少量精度换数量级加速**。
**HNSW**（Hierarchical Navigable Small World）：构建**多层邻近图**，上层稀疏用于快速跳转定位，底层稠密用于精确查找，查询复杂度接近 O(log N)，是目前综合性能最好的 ANN 索引之一。
本项目：内存库是**线性扫描**（全量精确，仅适合小规模）；Chroma 用 `hnsw:space=cosine` **就是 HNSW**（`ChromaStore` 建集合时指定）。

**78. 组成原理对 Embedding 推理性能的影响？**
Embedding/Cross-Encoder 推理是**密集矩阵乘**，性能受限于：①**CPU 浮点算力**（是否支持 AVX2/AVX-512 向量指令）；②**内存带宽**——1024 维 float 向量和模型权重要频繁从内存搬进 CPU 缓存，**带宽往往比算力更早成为瓶颈**；③**缓存命中率**——batch 推理能让权重常驻缓存，比逐条推理快一个数量级（代码里 `embed_batch` 就是为了这个）；④GPU 则用大规模并行单元和 HBM 高带宽，适合吞吐场景。

**79. 高并发进程模型？**
- **协程（asyncio）**扛 IO 并发：LLM 等待、DB、Redis——本项目主体
- **多进程（uvicorn --workers N 或 gunicorn）**绕开 GIL 并利用多核：每个 worker 独立进程
- **线程池**跑不可避免的同步 CPU 任务（重排、Embedding）
推荐组合：**多进程 × 协程**，CPU 密集再叠线程池。
**约束**：多进程会导致**内存会话不共享**——这又回到第 34 题，必须把会话外置 Redis 或做粘滞会话。

**80. MySQL 索引建在哪？慢查询怎么排查？**
索引（`app/models/database.py`）：
- `sessions.user_id`（`idx_user_id`）
- `messages.session_id`（`idx_msg_session`）——按会话查历史
- `unresolved_questions.resolved`（`idx_unresolved`）——筛未处理
- `operation_logs.(user_id, action)`（联合索引 `idx_op_user`）
另：主键 `user_id`、`session_id`、`doc_id`，`message_id/log_id/id` 自增主键。
慢查询排查：开 slow query log → `EXPLAIN` 看是否走索引、扫描行数、`type` 是否为 ALL → 检查是否索引失效（函数包裹、隐式类型转换、左模糊）→ 加索引或改写 SQL。

**81. 事务与隔离级别？项目里哪用了？**
隔离级别：MySQL 默认 **RR（可重复读）**，用 MVCC + 间隙锁；另有 RC / 读未提交 / 串行化。RR 下同一事务多次读一致性快照，能防不可重复读，配合间隙锁防幻读。
**项目中诚实回答**：本项目的 DB 写入都是**单条独立提交**（`persist_message`、`record_operation` 各自 `add + commit`），**没有显式使用多语句事务**，也没有用 `with db.begin()` 包裹跨表操作。跨系统一致性（写业务系统 + 写消息表）**没有用分布式事务**，靠"失败静默跳过 + 日志"降级——这在强一致场景是不够的，正确做法应是**本地消息表/事务性发件箱 + 对账补偿**。

## 七、前端（82-86）

**82. 界面是自己做的吗？什么技术？**
是，`web/` 下**原生三件套**：单个 `index.html` + `css/` + 一个 `js/app.js`，**没有用 React/Vue，也没有构建工具**（无 webpack/vite）。直接用 FastAPI 的 `StaticFiles` 挂载到根路径。

**83. 前端怎么对接 SSE？fetch 还是 EventSource？**
用的是 **`fetch` + `resp.body.getReader()`**，不是 `EventSource`。
原因：`EventSource` 只支持 **GET**，而对话接口是 **POST**（要传较长 message + session_id，且要带自定义头 `X-Demo-User`）。所以用 fetch 手动读流：
```js
const resp = await fetch("/api/v1/chat/stream", { method: "POST", headers: {...}, body: JSON.stringify({...}) });
const reader = resp.body.getReader();
// 按 \n 切行，识别 "event:" 与 "data:"，JSON.parse 后 handleEvent
```
`handleEvent` 按 `event` 名 switch：`session`（存 localStorage）、`token`（追加文本）、`sources`（渲染引用）、`done`（收尾），另有 `confirm`/`login_required` 等交互态。

**84. 多轮消息状态管理？**
**前端不存消息列表**，只存两个 id：`sessionId` 和 `userId`，都放 **localStorage**（`lib_session_id` / `lib_user_id`）。
**真正的会话状态在服务端**（`Session.messages` + `DialogueState`），前端只负责把 `session_id` 回传。需要历史时调 `GET /api/v1/chat/history/{session_id}`。
好处：多端一致、刷新不丢；风险：localStorage 里的 session_id 换设备就没了（真实场景应绑定登录态）。

**85. CSS 响应式怎么做？**（口径）
用**弹性布局 + 媒体查询**：聊天区用 flex 纵向布局自适应高度，消息气泡 `max-width` 百分比限宽；小屏下用 `@media` 调整侧栏（隐藏或抽屉化）、字号和输入区高度；输入框 `autoResize()` 随内容增高。
注意：本项目前端较简洁，**没有做完整的移动端断点体系**，若做一体机触屏（大屏）与手机（小屏）双端，需要单独设计两套布局。

**86. 重做前端选什么？**
（参考口径）会选 **Vue 3 + Vite**（或 React）：聊天界面有大量状态（消息列表、流式追加、会话阶段、引用卡片、登录态），框架能让**状态驱动渲染**而不是手动 DOM 操作；组件化便于做消息气泡、来源卡片、确认卡片；Vite 热更新快。
但当前项目体量小、单人开发，**原生 JS 零构建成本、加载快也合理**——选型要看团队和规模，不是越重越好。

## 八、简历拔高点核验（87-94）· 诚实收窄口径

> **通用原则**：被问到时**主动承认 + 说清现状 + 给出已设计的方案**。面试官要的是"你真懂取舍且不虚"，硬扛一旦被翻代码就是致命的。

**87. "基于 Redis 维护多轮对话上下文"，但代码是内存字典？**
"会话上下文我落地的是**进程内内存版**（`session_manager._sessions` 字典），**Redis 我实际用在了 FAQ 语义缓存和限流分布式计数**上。简历那句写的是目标架构，这点我如实说明。
多实例会遇到两个问题：会话丢失导致上下文断裂、二次确认的 `confirm_id` 找不到导致确认失败。外置方案我已经想清楚：把 `Session` 和 `DialogueState` 序列化存 Redis，坑在于含 `datetime` 对象要转 JSON（时间戳转 ISO 串），以及把 30 分钟/10 分钟超时映射成 Redis key 的 `EXPIRE`。"

**88. "混合检索（向量+关键词）"，但没有 BM25 索引？**
"严格说我不该叫它混合检索。我实现的是**单路向量召回 + 精排阶段融合字面特征**：`score = 0.75 × 语义cosine + 0.25 × 词项覆盖率`。
词项覆盖这 25% 是为了兜住'3楼''0.1元'这类专有名词的精确匹配，因为没有独立 BM25 索引，它依赖分词质量，遇到'三楼'vs'3楼'、同义词就弱。
真正的混合检索要另建 BM25 索引做第二路召回，再用 **RRF** 融合。代价是多维护一套索引、双写和分词一致性——这是我列在计划里的下一步。"

**89. "构建熔断与重试机制"，但只有降级？**
"**降级我有，熔断和重试确实没实现**，简历这句写得过了。降级是：LLM 失败走离线模板、稠密 Embedding 失败回退稀疏、Chroma 失败回退内存、Redis 失败回退进程内——每一层都有，且记 warning 日志。
缺熔断的危害我很清楚：上游超时时每个请求都傻等满 30 秒才降级，高并发会拖垮连接池。
补法不复杂：连续失败 5 次就打开 30 秒熔断，期间直接降级；用 tenacity 对超时/5xx 指数退避重试 2 次，4xx 不重试。"

**90. "接入结构化日志与链路追踪"，链路追踪用什么？**
"**链路追踪我实际没有集成组件**（没有 Jaeger/Zipkin/OpenTelemetry，也没有 trace_id 透传），简历这句我得修正。
我做的是**统一格式的日志**（`时间 | 级别 | 模块 | 消息`）和**运维看板数据接口**（`admin_service.get_overview()` 提供通道分布、未解决数、满意度等）。
如果要落地，我的方案是：一次请求一个 trace，span 划为 `gateway → ratelimit → classify → retrieve → rerank → llm.stream → persist`，tag 带 `session_id/intent/channel/top_k/llm_model`，用 OpenTelemetry 埋点导出到 Jaeger。"

**91. Docker Compose 包含哪些服务及依赖？**（这题**没有拔高**，可以自信答）
"三个服务：**app**（build 自 Dockerfile，端口 8000，挂载 `./data:/app/data`）、**mysql:8.0**（库 library_service，utf8mb4，卷 mysql_data）、**redis:7-alpine**。app 用 `depends_on` 声明依赖 mysql 和 redis。
app 的环境变量显式打开生产开关：`DEBUG=false`、`DB_ENABLED=true`、`REDIS_ENABLED=true`、`RATE_LIMIT_ENABLED=true`、`JWT_SECRET_KEY` 从宿主注入；RAG 三项（EMBEDDING_MODE / VECTOR_STORE_MODE / RERANKER_ENABLED）用 `${VAR:-默认值}` 注入，方便切换稠密向量和重排。"

**92. "未识别问题聚类模块"，但代码是频次统计？**
"**聚类算法我没实现**，做的是**频次统计**：`Counter` 累加问题，`most_common()` 出热门 Top-N。
两者的差距我很清楚：频次统计按**完全一致的字符串**计数，'续借怎么弄'和'如何续借'会被当成两个独立问题，馆员要重复处理。语义聚类（embedding + KMeans）能把同义不同表述归成一簇，一次标注覆盖一类。
所以我该把简历改成'**未识别问题记录与热度统计**'，聚类是下一步。"

**93. "BGE + Chroma + Cross-Encoder 重排"，但默认是 ngram + memory + 关闭重排？**
"这些能力**都实现了且可切换**，但**默认配置是演示友好的最小依赖组合**：`EMBEDDING_MODE=ngram`、`VECTOR_STORE_MODE=memory`、`RERANKER_ENABLED=false`。

所以准确表述是：**支持并在评测中对比验证过，生产按资源与质量需求开启**，而不是'生产默认在用'。"

**94. 哪一处最需要澄清？怎么诚实表达？**

①**生产中间件经验不足**——会话没外置 Redis、没有熔断重试、没有链路追踪，这些我在设计上想清楚了但没落地，缺真实高并发环境的锤炼。
②**评测体系不完整**——只覆盖了检索侧指标，生成侧（幻觉率、答案质量）没有自动化评测，闭环也缺真实线上轮次验证。
③**简历措辞有拔高**——我已经主动收敛（见第八类）。

**99. 入职后最想优化的三个点？**
**P0**：把会话外置到 Redis + 补熔断重试（这是多实例部署和稳定性的硬前提）。
**P1**：补生成侧评测（幻觉率 + LLM-as-judge 校准）并把评测接入 CI，让改 prompt 能自动回归。
**P2**：把未识别问题从频次统计升级为**语义聚类**，并用 CPU 密集任务线程池化解决事件循环阻塞。
（这三个点都对应真实缺口，讲得出代码落点，比喊"上 K8s/微服务"更可信。）

**100. 为什么做 AI/Agent 方向？1-3 年规划？**
（参考口径）因为 LLM 是少数能**直接把"理解自然语言"变成产品能力**的技术，而 Agent 让它从"会说"走向"会做"——这个转变里工程价值很大（编排、状态、降级、评测、成本），正好是我喜欢且擅长的系统性问题。
规划：1 年内把**工程底盘**补齐（分布式、可观测、评测体系、成本治理），能独立负责一个 AI 服务从 0 到线上；2-3 年深入 **Agent 编排与可靠性**（复杂任务规划、工具生态、多智能体协作），同时补齐大规模检索与推理优化的经验。
