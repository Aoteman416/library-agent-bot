# 零、60 秒开场脚本（"介绍一下你的项目吧"）

我最近做了一个**基于 RAG 的图书馆智能客服系统**。目标是用 AI 替代图书馆大量重复性咨询（查书、续借、座位预约、借书规则等），提供 7×24 小时自动服务。核心思路是用 RAG 让答案基于知识库、带引用来源，降低大模型幻觉。

技术上后端用 **FastAPI + Python**，自己搭了一条完整 RAG 链路：自适应分块 → Embedding → 向量检索 → 重排序 → 生成，前端静态页 + **SSE 流式输出**。我有四个可讲的亮点：
1. **三通道对话编排**（业务/FAQ/RAG）：确定性任务走业务通道，制度咨询走 FAQ/RAG，闲聊走兜底，各通道独立缓存与降级。
2. **DST 多轮状态机**：预约/续借用 `DialogueState` 结构化记录意图与槽位，缺啥追问啥，最后二次确认。
3. **双模式可降级**：没配 LLM Key 走离线模板照样能答；检索不到/超时都有兜底。
4. **评测闭环**：搭了基于人工标注问答对的检索质量评测（Recall/Precision/MRR），未解决问题回流知识库持续补录。

一句话：把 RAG、意图路由、多轮状态管理、流式输出、Function Calling 串成一条可落地、可评测、可降级的 AI 应用链路。

# 一、RAG 检索管道深度优化（简历模块 1）

## 简历原文
1) 自适应文档分块（政策按语义段落、FAQ 按问答对、指南按章节）；BGE-large-zh Embedding 向量化，存入 Chroma 并支持元数据过滤（分类、时间）。
2) 混合检索（向量+关键词）+ Cross-Encoder 重排序（bge-reranker-large），多级粗筛精排，提升相关性与排序质量。
3) 低置信度兜底（低分转人工或带引用免责声明）+ Prompt 强制约束"基于检索内容+引用来源"，抑制幻觉。

## 怎么讲（对齐代码）
- **分块**：`config.CHUNK_STRATEGY` 按文档类型配置不同 chunk_size/overlap（policy 500/100、faq 300/0、guide 800/150），`knowledge_service` 按文件名关键词自动判定类别并选用对应策略；`rag/chunker.py` 提供递归/问答对/章节三种切分。
- **Embedding 与向量库**：`EMBEDDING_MODE` 可在 `ngram`（零依赖稀疏，开箱即用）与 `external`（BAAI/bge-large-zh-v1.5 稠密）间切换；`VECTOR_STORE_MODE` 在进程内 `memory` 与 `Chroma` 间切换。`retriever.search` 支持 `metadata_filter`（按 source/category 过滤）。
- **检索与重排**：`Retriever.retrieve` 两阶段——向量初检 Top-K → 精排 Top-N。无重排器时用 `语义0.75 + 字面词项覆盖0.25` 的融合打分；开 `RERANKER_ENABLED` 后用 `bge-reranker-large` 做 Cross-Encoder 精排。`recall()` 提供纯向量召回用于评测。
- **兜底与约束**：`chat_service` 中 `RAG_LOW_CONFIDENCE_THRESHOLD` 低于阈值则记录到 `unresolved_questions` 并提示转人工/换关键词；`prompt_builder` 把"基于参考文档、不得编造、末尾标注 [来源]"写入系统提示。

## 面试官追问 + 参考答案
**Q1：为什么用 BGE 而不用 OpenAI text-embedding？**
A：项目偏私有化/低成本落地，BGE 是开源中文 SOTA、可本地部署不依赖外网，且支持查询侧指令前缀（`EMBEDDING_QUERY_PREFIX`）对齐语义空间；默认 ngram 则是为了零依赖开箱即用，两种模式用同一套接口切换。

**Q2：分块大小怎么定？切太大/太小有什么问题？**
A：经验 200–800 字符。太大→语义混杂、检索不精准、上下文浪费 token；太小→语义不完整、把一条规则拆散。所以按文档类型差异化：FAQ 按问答对切（overlap=0 不破坏配对），政策文件大块保上下文，指南按章节中等重叠。

**Q3：重排序（Reranker）相比只做向量检索好在哪？**
A：向量检索是"双塔"粗排，擅长召回但无法精细判断"查询-文档"相关性；Cross-Encoder 把查询和文档拼一起过一次编码器，相关性打分更准，能把真正相关的顶上来、滤掉语义相近但不相关的，显著提升 Top-N 精度。代价是推理慢，所以只用在粗筛后的 Top-K 上（多级粗筛精排）。

**Q4：怎么抑制幻觉？**
A：四道防线——①检索阶段提召回（Top-K + 元数据过滤）；②重排精排；③生成阶段 Prompt 强约束"只基于参考文档、无信息明确说不知道"+ 引用溯源；④无检索结果/低置信度直接转人工或带免责声明，绝不硬编。

**Q5：Chroma 和 FAISS 怎么选？**
A：Chroma 是开箱即用的向量库，支持元数据过滤与持久化，适合快速开发；FAISS 只是索引库，需要自己封装存储/过滤/服务。本项目选 Chroma 看重它的元数据和持久化能力。

## ⚠️ 防翻车
- **"混合检索（向量+关键词）"**：代码里**没有独立的 BM25/关键词索引**做召回融合。实际是"向量召回 + 精排阶段用字面词项覆盖率做融合打分（语义0.75+字面0.25）"。被追问时收敛为："以向量检索为主，在精排阶段融合了字面词项覆盖特征来兜住专有名词（如'3楼''0.1元'）的精确匹配"，不要说"双路召回再融合"。
- **"Chroma 向量库"**：默认是 `memory` 进程内模式，Chroma 需装 `requirements-rag.txt` 并改环境变量才启用。说"支持 Chroma"没问题，但别让面试官以为默认就是 Chroma。

# 二、Agent 工具调用与多轮对话管理（简历模块 2）

## 简历原文
1) 封装馆藏检索、续借、座位预约等业务 API 为标准 Tool，结合 LLM 的 Function Calling 实现自动路由决策，支持二次确认（续借需确认）。
2) 会话管理引擎：基于 Redis 缓存维护多轮对话上下文，滑动窗口 + Token 预算动态裁剪，兼顾连贯与成本。
3) 多意图问题澄清追问；越界问题礼貌拒答，提升复杂场景任务完成率。

## 怎么讲
- **Function Calling 路由**：`core/intent_rewriter.py` 定义 `route_intent` 工具（`chat_with_tools`），让 LLM 在低置信度时输出结构化 `{intent, query, book_title, date, start_time, end_time, area}`，实现"意图识别+查询改写+槽位抽取"一体。高置信度走 `IntentClassifier` 加权关键词分类（零依赖）。
- **二次确认**：`core/dst.py` 的 `DialogueState` 状态机 `idle→collecting_slots→confirming→completed`；续借/预约槽位填满后 `set_pending_confirm` 生成 `confirm_id`，用户回"确认"才 `seat_service.reserve()` / `user_service.renew()` 真正执行，带 5 分钟超时。
- **多轮上下文**：`core/session_manager.py` 的 `Session` 保存 `messages` 与 `DialogueState`；`MAX_HISTORY_TURNS=10`，存历史时截断到最近 20 条；公共设备 10 分钟、普通 30 分钟超时自动清除。
- **越界/澄清**：`core/security.py` 做 Prompt 注入防护与越界礼貌拒答；`IntentClassifier` 有业务 vs FAQ 的冲突消解（相似度≥80% 时优先 FAQ）。

## 面试官追问 + 参考答案
**Q1：Function Calling 在这里具体怎么用的？为什么不直接让 LLM 自由输出 JSON？**
A：用 `route_intent` 工具让模型"调用函数"输出结构化参数，schema 由模型原生保证合法，比自由文本 JSON 稳定得多。它承担三件事：判断意图、把口语改写规范查询（"有三体吗"→查书《三体》）、抽取业务槽位（预约的日期/时间/区域）。

**Q2：多轮对话的上下文怎么管理，会不会超 token？**
A：每会话保留最近 N 轮消息，超出截断；同时在 `build_context` 阶段按系统提示/检索块/历史/查询分配 token 预算，优先保检索内容与近期历史。公共设备会话更短超时，避免隐私泄露。

**Q3：槽位没收集齐怎么办？多个槽位怎么追问？**
A：`DialogueState` 记录每个槽位是否 filled，`next_question()` 追问第一个缺失槽位；用户一句话可同时填多个槽位（`extract_entities` 抽时间/日期/区域 + Function Calling 预抽）。齐了才进确认阶段。

**Q4：用户说"帮我续借"，但没说哪本书，怎么处理？**
A：进 `borrow_manage` 槽位收集，从历史里用正则`《...》`找书名；找到就填入，没找到就追问"请告诉我要续借的书名或编号"，集齐后二次确认再执行，避免误操作。

**Q5：和 LangChain 的 Agent/Tool 有什么区别？**
A：我没有用框架，而是手写了"意图路由 + DST 状态机 + 业务服务"的轻量编排，依赖更轻、每一环可控可调。Function Calling 只用于"路由与抽取"，真正的业务执行由确定性代码（`book/seat/user_service`）完成，不是让 LLM 自由调工具，更安全可预期。

## ⚠️ 防翻车（本节最危险）
- **"基于 Redis 缓存维护多轮对话上下文"**：❌ **代码没这么做**。`SessionManager` 把会话存在**进程内存字典** `_sessions`，Redis 只用于 FAQ 语义缓存和限流计数。被追问务必收敛为："会话状态当前是进程内内存管理（单机），热点问答缓存和限流计数用 Redis；多实例部署时会话可改造为走 Redis/外部存储"。不要说会话上下文存在 Redis。
- **"Token 预算动态裁剪"**：实际是**按消息条数**（`MAX_HISTORY_TURNS*2=20`）截断，并非真实 token 计数预算。说"保留最近 N 轮、超出截断"即可，别强调"token 预算"这个听起来很精确的词，被追问就说"按轮次+阶段分配预算的简化实现"。

# 三、高可用工程化落地（简历模块 3）

## 简历原文
1) FastAPI 构建 RESTful + SSE 流式接口，低延迟流式输出；JWT 认证、用户级限流、Redis 缓存热点问答。
2) 服务降级（LLM 不可用切关键词匹配库）；熔断与重试机制；Docker Compose 全服务容器化。
3) 可观测性：结构化日志 + 链路追踪；运维看板实时监控核心指标。

## 怎么讲
- **接口与流式**：`main.py` 用 `lifespan` 启动建库建索引；`api/v1/chat.py` 用 `StreamingResponse` 逐 token 推 SSE 事件（`route/token/sources/confirm/done/login_required/error`）。
- **鉴权与限流**：`core/auth.py` JWT + Refresh Token；`core/ratelimit.py` 双维度滑动窗口（per_user=30、per_ip=100/60s），超限返 429 带 `Retry-After`，优先 Redis 分布式计数、否则进程内。
- **降级**：`rag_service` 未配 Key/调用失败 → 离线模板（拼检索块）；`chat_service` 低置信度/unknown → 转人工或闲聊兜底；DB 不可用 → 内存演示静默跳过。
- **部署**：`Dockerfile`（python:3.11-slim）+ `docker-compose.yml`（app+mysql+redis），生产环境关 DEBUG、开鉴权/限流/持久化。
- **可观测性**：`core/logger.py`（loguru 结构化日志）；`admin_service` 提供 overview（通道占比、满意度、未解决数）、hot-questions、反馈评分，即运维看板数据来源。

## 面试官追问 + 参考答案
**Q1：SSE 流式是怎么实现的？和 WebSocket 区别？**
A：用 `StreamingResponse` + `media_type="text/event-stream"`，`async for` 逐块 `yield` `data: {...}\n\n`。SSE 是单向（服务端→客户端）、基于 HTTP、自动重连，适合问答流式推送；WebSocket 是双向全双工，更适合需要客户端频繁发指令的场景。客服问答是"用户一句、模型流式回"，SSE 更轻。

**Q2：限流怎么做的？分布式部署下准吗？**
A：滑动窗口，按用户（解析 JWT sub）和 IP 双维度计数。配了 Redis 就用 `INCR+EXPIRE` 做分布式计数，多实例一致；没配就进程内 deque，单机准确、多实例各自计。生产 compose 里已启用 Redis。

**Q3：LLM 挂了系统还能答吗？**
A：能。没配 Key 或调用异常时，`rag_service` 自动降级到"离线模板"——直接用检索到的知识块拼装回答；闲聊/未知意图走兜底话术或转人工。核心是任何一层失败都不抛给用户一个 500，而是有可接受的降级答案。

**Q4：JWT 为什么还要 Refresh Token？**
A：Access Token 短时效（60 分钟）降低泄露风险，过期用 Refresh Token（7 天）无感续期，避免用户频繁重新登录；Refresh 也可在后端吊销。

## ⚠️ 防翻车
- **"熔断与重试机制"**：❌ **代码没有真正的熔断器（Circuit Breaker）或重试逻辑**。只有"降级"（degrade）。被追问务必收敛为："实现了服务降级与失败兜底（LLM 不可用自动切模板、DB 不可用走内存演示），重试/熔断在网关层或后续接入（如用 tenacity/熔断中间件）"——不要说"我实现了熔断"。
- **"链路追踪"**：❌ **没有** OpenTelemetry/分布式 tracing。只有 loguru 结构化日志。说"结构化日志 + 关键路径打点 + admin 看板指标"即可，明确别提 tracing。
- **"运维看板"**：是 `admin_service` 的**统计接口**（通道占比/满意度/热门问题），不是独立可视化前端。说"提供了运营统计接口与数据闭环"更准。

# 四、质量评估与持续迭代（简历模块 4）

## 简历原文
1) 主导构建 RAG 质量评估体系：基于人工标注问答对搭评测集，围绕召回质量、精准程度、幻觉率等维度建立自动化回归测试。
2) 未识别问题聚类模块，定期将低置信度问答回流知识库人工标注补录，形成"数据→评测→优化"迭代闭环。

## 怎么讲
- **评测体系**：`eval/run_eval.py` + `data/eval/qa_eval.jsonl`（人工标注，每条标了期望命中的 source/category 与必含关键词）。指标：`Recall@K / Precision@K / HitRate@K / MRR / KeywordHit@K`，相关判定按"知识条目粒度"（source+category 同时命中）。支持 `--compare` 稀疏 vs 稠密、`--no-rerank` 只测召回，输出 `report.md/json`。
- **闭环回流**：`chat_service` 低置信度问题写入 `unresolved_questions`；`admin_service` 收集反馈（低分≤3 自动进待回流）、`get_hot_questions` 频次统计、`resolve_unresolved` 让馆员补答案后入 `pending_knowledge` 回流知识库。

## 面试官追问 + 参考答案
**Q1：怎么衡量 RAG 效果好不好？指标怎么定义的？**
A：检索侧用 Recall@K（召全）、Precision@K/MRR（排得准、首条命中）、KeywordHit@K（Top-K 文本是否覆盖必含关键词，间接反映"能不能直接答"）；生成侧靠引用准确率+人工抽检。相关判定以"知识条目"为最小粒度而非整篇文档，更准。

**Q2：幻觉率怎么测？**
A：本项目用"关键词命中率 + 引用来源准确率 + 低置信度转人工比例"作为幻觉的代理指标；更严谨的做法是人工标注答案是否含知识库外信息，或用 LLM-as-judge 对"答案是否可由检索内容支撑"打分。这是我们后续要补的。

**Q3：评测怎么融入迭代？**
A：`run_eval.py` 跑出未达标样本清单（召回失败/关键词缺失），直接定位是分块问题、Embedding 问题还是知识库缺内容；运营侧把低置信度/低分问题回流，馆员补录后重新评测，形成"数据→评测→优化"闭环。

## ⚠️ 防翻车
- **"未识别问题聚类模块"**：❌ **没有真正的聚类算法**（如 KMeans/语义聚类）。实际是"记录 + 频次统计（`most_common` 热门问题）+ 人工标注回流"。被追问收敛为："对未识别问题做了记录与频次统计，并支持人工标注补录回流；语义聚类（自动归并相似问题）是计划中的下一步"，别说"实现了聚类模块"。

| 未识别问题聚类 | 记录 + 频次统计 + 人工回流，无聚类算法 | "记录与频次统计 + 人工标注回流；语义聚类是下一步" |
| Chroma 向量库 | 默认 memory，Chroma 需装依赖启用 | "支持 Chroma，默认内存模式开箱即用" |

> 原则：**能讲清设计思路与取舍，比硬撑一个没实现的词更重要**。面试官更看重你是否真懂，收敛口径反而加分。

# 六、通用面试问题（技术深挖 + 项目/行为）

## 技术深挖
1. **为什么不用现成框架（LangChain/LlamaIndex）？** → 自研更轻、可控、每环可调，且能讲清每一步原理；框架黑盒不利于面试展示深度。（见模块二 Q5）
2. **RAG 和微调（Fine-tuning）怎么选？** → 知识频繁更新选 RAG（更新知识库即可，不必重训）；风格/格式固化且数据 Stable 才考虑微调；本项目知识常变，RAG 更合适。
3. **向量检索的相似度度量用什么？** → 余弦相似度（归一化内积）；稠密 BGE 用余弦，稀疏 ngram 用 TF-IDF 向量余弦。
4. **高并发下 SSE 会阻塞吗？** → FastAPI 异步 + `async for` 流式 yield，单连接不阻塞事件循环；配合限流与 uvloop 扛量；真正高并发可加反向代理（Nginx）与多 worker。
5. **怎么做鉴权与多角色（学生/教师/管理员）？** → JWT 携 role 声明；`core/permissions.py` 做功能级权限矩阵，敏感操作（续借/预约）需登录。
6. **Prompt 注入怎么防？** → `security.py` 检测注入模式与越界话题，命中拦截；系统提示与用户内容隔离，检索内容作为上下文而非可执行指令。

## 项目 / 行为题
7. **这个项目你遇到的最大难点是什么？怎么解决的？**
   → 建议讲"多轮业务对话的状态一致性"：预约/续借要跨多轮收集槽位且不能丢。解法是用 DST 显式状态机替代隐式历史拼接，并加二次确认防误执行。
8. **如果让你重做，会改什么？**
   → 会话状态外置到 Redis 支持多实例；引入语义聚类自动归并未识别问题；生成侧加 LLM-as-judge 自动评测幻觉；补真正的熔断。
9. **你怎么验证你的方案有效？**
   → 用 `eval/run_eval.py` 在人工标注集上量化 Recall/MRR/KeywordHit，对比"有无重排""稀疏 vs 稠密"，用数据驱动调参。
10. **这个项目的业务价值？**
    → 把占馆员大量时间的重复咨询自动化，7×24 自助，且答案可溯源降低投诉与误导风险；未解决问题回流形成可持续优化的知识运营闭环。

## 一问一答速记（若时间紧只背这些）
- 是什么：FastAPI+RAG 的图书馆智能客服，三通道对话编排 + DST 多轮 + SSE 流式 + 离线可降级。
- 最大亮点：三通道分离 + DST 状态机 + 双模式降级，工程鲁棒性强。
- RAG 流程：分块→Embedding→向量召回→Cross-Encoder 重排→Prompt 约束生成+引用。
- 防幻觉：检索提召回 + 重排精排 + Prompt 强约束 + 引用溯源 + 低分转人工。
- 多轮：DialogueState 状态机 + 槽位填充 + 二次确认（5 分钟超时）。
- 高可用：SSE 流式 + JWT + 限流 + 降级兜底 + Docker Compose。
- 评测：人工标注集量化 Recall/MRR/KeywordHit，未解决问题回流形成闭环。
